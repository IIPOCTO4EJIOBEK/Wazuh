# 15. Вход по учётным записям Active Directory

Вход в дашборд работает по доменным учётным записям — так же, как в
Zabbix, и через тот же контроллер домена. Отдельные пароли для Wazuh
никому не заводятся.

Настройка вынесена в Ansible и применяется вместе с остальной
конфигурацией индексера. Правки на стенде руками переживут ровно до
следующего прогона плейбука.

---

## Как устроено

Проверка подлинности идёт по двум источникам, в строгом порядке.

| Порядок | Источник | Кто там | Когда используется |
|--------:|----------|---------|--------------------|
| 1 | внутренняя база индексера | `admin`, `kibanaserver`, `filebeat`, `snapshotter` | служебные учётные записи, работают всегда |
| 2 | Active Directory | люди | обычный вход в интерфейс |

Порядок выбран не случайно. **Внутренняя база проверяется первой**,
чтобы недоступность контроллера домена не отрезала администратора от
собственной системы. Именно учётной записью `admin` восстанавливают
доступ, когда каталог не отвечает, — а он не отвечает ровно тогда, когда
в домене что-то случилось и в SIEM надо срочно.

## Права

Выданы по образцу Zabbix: полный доступ поимённо, остальным — чтение.

| Кто | Роль | Что может |
|-----|------|-----------|
| Список из `indexer_admin_users` | `all_access` | всё, включая настройки платформы |
| Любой прошедший проверку | `wazuh_reader` + `kibana_read_only` | читать алерты и уязвимости |

Список администраторов задаётся одной переменной в
`ansible/group_vars/all.yml`:

```yaml
indexer_admin_users:
  - "tsekhovskoy.va"
  - "dulepov.av"
  # ...
```

Правится там, а не в шаблоне и не на стенде.

---

## Настройка

```yaml
# ansible/group_vars/all.yml
ldap_enabled: true
ldap_hosts:
  - "10.1.20.21:389"
ldap_bind_dn: "CN=zabbix_tech,OU=Tech Users,OU=Special,DC=rusagroeco,DC=ru"
ldap_userbase: "DC=rusagroeco,DC=ru"
ldap_usersearch: "(sAMAccountName={0})"
ldap_username_attribute: "sAMAccountName"
```

```yaml
# ansible/group_vars/vault.yml — под ansible-vault
vault_ldap_bind_password: "пароль технического пользователя"
```

Применение:

```bash
ansible-playbook -i inventory/pilot/hosts.yml site.yml \
                 --tags indexer,indexer-init --ask-vault-pass
```

Конфигурация каталога сама по себе не подхватывается — её загружает
`securityadmin.sh`, и это делает тег `indexer-init`. Правка файла на
диске без загрузки не даёт ничего.

## Три ошибки, на которых теряют время

Все три проверены на пилоте, каждая выглядит как «просто не пускает».

### Ключ `hosts`, а не `servers`

Индексер Wazuh — форк OpenSearch Security **ветки 1.x**. Сервер каталога
задаётся так:

```yaml
hosts:
  - 10.1.20.21:389        # адрес и порт, без схемы
```

Форма из версии 2.x — `servers: ["ldap://10.1.20.21:389"]` — молча не
читается. Симптом: любой вход даёт 401, а в журнале индексера видно, что
подключение идёт совсем не туда:

```
Unable to connect to any of those ldap servers [localhost]
```

Ключевое слово в этой строке — `localhost`. Значит, адрес не прочитан
вообще, и дело не в пароле и не в правах.

### Обязательный `username_attribute`

Без него пользователь представляется полным различающим именем:

```
CN=Цеховской Владимир,OU=Users,DC=rusagroeco,DC=ru
```

Проверка подлинности при этом проходит, а сопоставление ролей по имени
(`tsekhovskoy.va`) — нет. Человек входит и видит пустой интерфейс без
единого индекса. Выглядит как проблема с правами, лечится одной строкой:

```yaml
username_attribute: "sAMAccountName"
```

### Окно входа запрашивает не ту учётную запись

Управляется параметром `challenge`. У домена каталога он `true`, у
внутренней базы при этом `false` — иначе браузер спрашивает внутреннюю
учётную запись и доменную не принимает. Шаблон выставляет это
автоматически, вручную выравнивать не нужно.

## Проверка

```bash
# Технический пользователь виден каталогу и получает роли
curl -sk -u "zabbix_tech:ПАРОЛЬ" \
  https://10.17.1.252:9200/_plugins/_security/authinfo

# Ожидается: user_name, roles [own_index, kibana_read_only, wazuh_reader]

# Доменный пользователь принимается дашбордом
curl -sk -o /dev/null -w '%{http_code}\n' -u "tsekhovskoy.va:ПАРОЛЬ" \
  https://10.17.1.252/api/status        # 200

# Неверный пароль отвергается
curl -sk -o /dev/null -w '%{http_code}\n' -u "tsekhovskoy.va:НЕВЕРНЫЙ" \
  https://10.17.1.252/api/status        # 401
```

Если вход не проходит, подробности — в журнале индексера:

```bash
tail -f /var/log/wazuh-indexer/wazuh-ahp.log
```

Временно включить подробный вывод по каталогу:

```bash
curl -sk -u admin -X PUT 'https://10.17.1.252:9200/_cluster/settings' \
  -H 'Content-Type: application/json' -d '{
  "transient": {
    "logger.com.amazon.dlic.auth.ldap": "DEBUG",
    "logger.org.opensearch.security.auth": "DEBUG"
  }}'
```

После разбора вернуть в `INFO`: на уровне DEBUG журнал растёт быстро.

## Что осталось сделать по каталогу

**Перевести права на группы безопасности.** Сейчас список
администраторов ведётся поимённо, и при кадровом изменении его правят
руками. Роли по группам избавляют от этого: человека добавили в группу —
права появились.

Механизм готов и выключен переменной:

```yaml
ldap_group_authz: true
ldap_rolebase: "OU=Groups,DC=rusagroeco,DC=ru"
```

Нужны заведённые группы в каталоге, например `WAZUH-Admins` и
`WAZUH-Readers`, и сопоставление их с ролями индексера. Пока групп нет,
переменная остаётся выключенной.

**Учесть при переходе на отказоустойчивую схему.** Конфигурация каталога
загружается в кластер целиком и хранится в индексе, а не на диске узла.
При добавлении узлов ничего заново настраивать не нужно, но
`securityadmin.sh` после изменений запускается по-прежнему с одного узла.
