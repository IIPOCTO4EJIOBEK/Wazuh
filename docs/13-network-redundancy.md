# 13. Резервирование сети на узлах

Один сетевой интерфейс на узле — такая же точка отказа, как один узел в
кластере. Разница в том, что отказ интерфейса выглядит хуже: узел жив,
процессы работают, а кластер считает его выпавшим и начинает
перебалансировку.

Документ разбирает резервирование сети снизу вверх: интерфейс, коммутатор,
шлюз, канал между площадками. Числа приведены для интерфейсов 1 Гбит/с.

---

## Сначала — где именно резервировать

Это первое, что нужно понять, иначе работа делается впустую.

**Узлы платформы — виртуальные машины.** Основной гипервизор компании —
pdc-hv0, FUJITSU RX2540 M5 под Windows Server 2022. Для виртуальной
машины объединение интерфейсов настраивается **на гипервизоре**, а не
внутри гостевой системы.

Две виртуальные сетевые карты, подключённые к одному виртуальному
коммутатору, и объединённые внутри гостя в bond — конструкция, которая
выглядит как резервирование и им не является: обе карты идут через один
и тот же виртуальный коммутатор и один и тот же физический порт. Отказ
физического порта унесёт обе.

| Что за узел | Где настраивать |
|-------------|-----------------|
| Виртуальная машина на Hyper-V | Teaming на хосте (SET), гостю — одна vNIC |
| Виртуальная машина на VMware | NIC teaming на vSwitch, гостю — одна vNIC |
| Физический сервер | bonding в самой системе |

Ниже разобраны оба случая.

---

## Виртуальные машины: teaming на гипервизоре

На Hyper-V используется Switch Embedded Teaming — объединение встроено в
виртуальный коммутатор.

```powershell
# Два физических адаптера в один коммутатор
New-VMSwitch -Name "SET-Wazuh" `
             -NetAdapterName "NIC1","NIC2" `
             -EnableEmbeddedTeaming $true `
             -AllowManagementOS $true

# Распределение по портам виртуальных машин
Set-VMSwitchTeam -Name "SET-Wazuh" -LoadBalancingAlgorithm HyperVPort

# Проверка
Get-VMSwitchTeam -Name "SET-Wazuh" | Format-List Name, NetAdapterInterfaceDescription, LoadBalancingAlgorithm
Get-NetAdapter | Where-Object Name -like "*NIC*" | Format-Table Name, Status, LinkSpeed
```

Важно: SET работает только в режиме, независимом от коммутатора — LACP
здесь не настраивается и не нужен. Это не ограничение, а преимущество:
два адаптера можно завести в **два разных коммутатора**, и тогда
резервируется не только кабель, но и сам коммутатор.

Виртуальной машине выдаётся одна сетевая карта. Никакого bonding внутри
гостя.

---

## Физические серверы: bonding

Если узел ставится на железо, объединение настраивается в системе. Для
Ubuntu 24.04 — через netplan.

### Режимы и когда какой

| Режим | Полоса | Переживает отказ коммутатора | Требует настройки коммутатора |
|-------|--------|------------------------------|-------------------------------|
| `active-backup` | 1 Гбит | **да**, если карты в разные коммутаторы | нет |
| `802.3ad` (LACP) | до 2 Гбит суммарно | только при стеке или MLAG | да, обе стороны |
| `balance-tlb` / `alb` | до 2 Гбит | да | нет |

**Для узлов Wazuh рекомендуется `active-backup`** — при условии, что
карты уходят в два независимых коммутатора. Причина в следующем разделе:
LACP всё равно не ускорит то, ради чего его обычно берут.

### Настройка active-backup

```yaml
# /etc/netplan/60-wazuh-bond.yaml
network:
  version: 2
  renderer: networkd

  ethernets:
    eno1:
      dhcp4: no
      dhcp6: no
    eno2:
      dhcp4: no
      dhcp6: no

  bonds:
    bond0:
      interfaces: [eno1, eno2]
      addresses: [10.5.2.81/24]
      routes:
        - to: default
          via: 10.5.2.1
      nameservers:
        addresses: [10.1.20.41, 10.0.2.10]
      parameters:
        mode: active-backup
        primary: eno1
        # Опрос состояния канала каждые 100 мс
        mii-monitor-interval: 100
        # Не возвращаться на основную карту мгновенно: порт коммутатора
        # успевает подняться раньше, чем начинает передавать трафик
        up-delay: 200
        down-delay: 0
```

```bash
netplan try            # применить с откатом через 120 с, если связь пропала
netplan apply
cat /proc/net/bonding/bond0
```

Вывод должен показывать `Currently Active Slave: eno1` и обе карты в
состоянии `up`.

### Настройка LACP

Применима, только если оба порта идут в один коммутатор либо в стек
(MLAG). Иначе агрегация не соберётся.

```yaml
  bonds:
    bond0:
      interfaces: [eno1, eno2]
      addresses: [10.5.2.81/24]
      parameters:
        mode: 802.3ad
        lacp-rate: fast          # обмен раз в секунду вместо раз в 30
        mii-monitor-interval: 100
        transmit-hash-policy: layer3+4
```

`layer3+4` распределяет по паре «адрес плюс порт»: без него весь трафик
между двумя узлами кластера ляжет на одну карту.

---

## Почему 2 × 1 Гбит не дают 2 Гбит там, где нужно

Распространённое заблуждение, из-за которого LACP берут напрасно.

Агрегация распределяет **потоки**, а не байты внутри потока. Одно
TCP-соединение всегда целиком идёт через одну физическую карту. Отсюда:

* **Восстановление узла индексера** — несколько параллельных потоков
  (по умолчанию два файловых чанка). Прирост от второй карты в лучшем
  случае двукратный на короткое время, чаще — никакого.
* **Репликация в обычном режиме** — около 0,6 Мбит/с. Вторая карта не
  нужна ни при каких обстоятельствах.
* **Много агентов** — вот здесь LACP работает: четыреста соединений
  распределяются по картам равномерно. Но 400 агентов дают около
  3 Мбит/с в пике, и 1 Гбит перекрывает это с запасом в триста раз.

Вывод: на этих объёмах вторая карта нужна для **отказоустойчивости**, а
не для полосы. Значит и режим выбирается тот, который лучше резервирует:
`active-backup` в два коммутатора.

---

## Коммутаторы: без этого резервирование бессмысленно

Две карты в один коммутатор защищают от обрыва кабеля и отказа порта. От
отказа коммутатора, потери им питания и перезагрузки при обновлении
прошивки — не защищают.

```
   ПРАВИЛЬНО                         НЕПРАВИЛЬНО
   ┌──────────┐                      ┌──────────┐
   │  сервер  │                      │  сервер  │
   └─┬──────┬─┘                      └─┬──────┬─┘
     │      │                          │      │
  ┌──▼──┐ ┌─▼───┐                    ┌─▼──────▼─┐
  │ SW1 │ │ SW2 │                    │   SW1    │
  └──┬──┘ └─┬───┘                    └────┬─────┘
     └──┬───┘                             │
        ▼                                 ▼
```

**Сходимость сети важнее скорости переключения bond.** Bond переключает
карту за 200 мс, а протокол связующего дерева на неподготовленном порту
переводит его в передачу за 30 секунд. Тридцать секунд молчания кластер
индексера трактует как выпадение узла: начинается перевыбор и
перебалансировка шардов. То есть настроенный bond при ненастроенных
портах делает хуже, чем его отсутствие.

Порты серверов обязаны быть краевыми:

```
# MikroTik (RSTP)
/interface bridge port set [find interface=ether5] edge=yes point-to-point=yes

# Cisco-совместимый синтаксис
interface GigabitEthernet0/5
 spanning-tree portfast
 spanning-tree bpduguard enable
```

Проверка того, что сходимость укладывается в секунду:

```bash
# на узле, во время выдёргивания кабеля из активной карты
ping -i 0.2 10.5.2.1 | ts
```

Пропасть должно не больше пяти-шести ответов. Если пропадает тридцать
секунд — портфаст не включён.

---

## Шлюз: резервировать тоже

Вторая карта, ведущая к тому же единственному маршрутизатору, оставляет
точку отказа на месте. Шлюз резервируется отдельно — VRRP на паре
маршрутизаторов, виртуальный адрес как шлюз по умолчанию:

```
# MikroTik, пара маршрутизаторов
/interface vrrp add name=vrrp-wazuh interface=bridge-lan vrid=10 priority=200
/ip address add address=10.5.2.1/24 interface=vrrp-wazuh
```

Проверка — тот же принцип: выключить основной маршрутизатор и убедиться,
что связь восстанавливается за секунды, а кластер индексера остался
`green`.

---

## Что поправить в конфигурации платформы

**keepalived привязан к имени интерфейса.** После перехода на bond имя
меняется, и виртуальные адреса не поднимутся:

```yaml
# ansible/group_vars/all.yml
wazuh_vrrp_interface: "bond0"     # было eth0
```

**Скорость восстановления узла ограничена не каналом.** По умолчанию
OpenSearch ограничивает восстановление сорока мегабайтами в секунду
независимо от того, какой канал под ним. При полной копии около 400 ГБ
это почти три часа на канале, который прокачал бы её за час.

```bash
# поднять предел, когда канал 1 Гбит
curl -k -u admin -X PUT 'https://10.5.2.81:9200/_cluster/settings' \
  -H 'Content-Type: application/json' -d '{
  "persistent": {
    "indices.recovery.max_bytes_per_sec": "250mb",
    "indices.recovery.max_concurrent_file_chunks": 4
  }}'
```

| Предел | Время восстановления 400 ГБ |
|--------|----------------------------:|
| 40 МБ/с (по умолчанию) | ~2 ч 50 мин |
| 250 МБ/с, канал 1 Гбит | ~1 ч |
| 250 МБ/с, канал 100 Мбит/с | ~9 ч |

Ограничение стоит снимать на время восстановления и возвращать обратно:
восстановление на полной скорости съедает канал, по которому в это же
время идут события.

**Таймауты кластера трогать не нужно.** Обнаружение выпавшего узла
занимает около тридцати секунд, переключение bond — доли секунды.
Запаса достаточно, и уменьшать чувствительность кластера ради сетевых
переключений не требуется.

## Канал между площадками

Для геосхемы ([12-geo-distribution.md](12-geo-distribution.md))
резервируется не карта, а маршрут. Требования там же; здесь — как
получить два независимых пути.

**Два провайдера, а не два кабеля одного.** Второй кабель того же
оператора идёт по той же трассе и рвётся тем же экскаватором.

**Туннель поверх обоих.** Между площадками поднимается WireGuard или
IPsec, а выбор физического пути отдаётся маршрутизации. Тогда разрыв
основного канала не рвёт сессии кластера — меняется только маршрут
внутри туннеля.

```
# MikroTik: два провайдера, проверка живости, переключение
/ip route add dst-address=<сеть площадки 2> gateway=<ISP1> distance=1 \
    check-gateway=ping comment="основной"
/ip route add dst-address=<сеть площадки 2> gateway=<ISP2> distance=2 \
    comment="резервный"
```

**LTE как резерв — только для управления.** В сети компании уже есть
LTE-модем (`10.5.24.150`, и по инвентаризации у него нулевой баланс —
что само по себе показывает, чего стоит непроверяемый резерв). Через LTE
можно достучаться до узлов и снять состояние. Держать на нём репликацию
индексера нельзя: задержка и потери выбьют узел из кластера, а трафик
восстановления исчерпает трафик тарифа за часы.

Правильное поведение при уходе на LTE — не «продолжать как ни в чём не
бывало», а осознанно перевести площадку в режим одиночной работы.

## Проверка

Резервирование, которое не проверяли выдёргиванием кабеля, не
резервирование. Порядок — тот же, что для учений по отказоустойчивости:
вне рабочих часов, с предупреждением дежурного.

```bash
# 1. Что сейчас активно
cat /proc/net/bonding/bond0 | grep -E "Active Slave|MII Status"

# 2. Фоновая проверка связности в отдельном окне
ping -i 0.2 10.5.2.1 | ts '[%H:%M:%.S]'

# 3. Выдернуть кабель активной карты. Ожидание:
#    пропадает не больше 5–6 ответов, Active Slave меняется на eno2

# 4. Кластер не заметил
curl -sk -u admin 'https://10.5.2.81:9200/_cluster/health?pretty' | grep status

# 5. Вернуть кабель, через 200 мс + up-delay вернуться на eno1
```

Что проверить дополнительно:

- [ ] Отключение первого коммутатора целиком — узлы остались на связи
- [ ] Отключение основного маршрутизатора — VRRP переключил шлюз
- [ ] Кластер индексера всё это время оставался `green`
- [ ] Агенты не переподключались (в журнале менеджера нет всплеска)
- [ ] Виртуальные адреса keepalived остались на своих узлах

Последний пункт особенно важен: если при пропадании карты на секунду
уехал виртуальный адрес приёма агентов, значит проверка живости в
keepalived слишком чувствительна, и её пороги надо поднять.

## Итог

| Уровень | Чем резервируется | Что даёт |
|---------|-------------------|----------|
| Карта и кабель | teaming на гипервизоре либо bond active-backup | отказ порта и обрыв кабеля |
| Коммутатор | две карты в два независимых коммутатора + RSTP edge | отказ и перезагрузка коммутатора |
| Шлюз | VRRP на паре маршрутизаторов | отказ маршрутизатора |
| Канал между площадками | два провайдера, туннель поверх, маршрутизация по доступности | обрыв магистрали |
| Площадка | третья точка с арбитром | пожар, электричество, СХД |

Каждый уровень закрывает свой отказ и не закрывает соседние. Bond без
второго коммутатора, второй коммутатор без резервного шлюза и резервный
шлюз без второй площадки — это три разные степени готовности, и стоит
понимать, на какой из них компания находится сейчас.
