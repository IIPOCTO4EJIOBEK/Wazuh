# 07. Обнаружение и реагирование

## Уровни и что за ними следует

| Уровень | Что происходит | Кто реагирует |
|---------|----------------|---------------|
| 3–6 | только в дашборд | никто, смотрят при разборе |
| 7–9 | в дашборд | дежурный в рабочее время |
| 10–11 | почта + Telegram | дежурный, в течение часа |
| 12–14 | заявка в ServiceDesk Plus + Zabbix | немедленно |
| 15 | то же + автоматическое действие | немедленно |

Уровень 15 означает, что система уже что-то сделала: заблокировала
адрес, изолировала станцию или отключила учётную запись. Человек
разбирается с последствиями, а не предотвращает событие.

## Собственные правила

Диапазоны идентификаторов:

| Файл | Диапазон | О чём |
|------|----------|-------|
| `local_rules.xml` | 100000–100099 | защита платформы, аутентификация, привилегии |
| `ahp_bitrix_rules.xml` | 100200–100299 | портал, заявки, СУБД, веб-атаки |
| `ahp_windows_ad_rules.xml` | 100300–100399 | Windows, Active Directory, вредоносное ПО |
| `ahp_infrastructure_rules.xml` | 100400–100499 | диски, СХД, балансировщик, MSSQL, резервные копии |
| `ahp_ioc_rules.xml` | 100500–100599 | инструменты атакующего, запуск из служебных каталогов, шифровальщик |
| `ahp_tuning.xml` | 100900–100999 | снятие ложных срабатываний |

### Правила, за которыми стоит конкретная история

**100201–100205, целостность `/home/bitrix/www`.** Каталог доступен на
запись учётной записи разработчика и группе `bitrix`. Файлы формы
заявки, обработчиков и журнал с персональными данными сотрудников лежат
там же. Подмена файла — самый вероятный способ закрепиться, и самый
заметный, если следить в реальном времени с записью различий.

**100410–100414, дисковая подсистема.** 09.06.2026 на pdc-hv0
(10.2.27.118) отказал массив FUJITSU ETERNUS_DXL: в 17:37 ошибка
`0x80000011` на `HarddiskVolume10`, через 47 секунд перезагрузка
сервера, в 17:59 повреждение файловой системы и потеря части отложенной
записи. Ни одно из этих событий не подняло тревогу вовремя — их увидели
постфактум, разбирая журналы. Правило 100414 срабатывает именно на эту
последовательность: дисковое событие, а следом перезагрузка того же
узла в течение десяти минут.

**100005, молчание агента на критичном узле.** Отсутствие событий с
контроллера домена внешне неотличимо от успешного отключения
журналирования атакующим. Для рядового узла это уровень 5, для узла из
списка `ahp-critical-hosts` — 12.

**100311–100312, шифровальщик.** Удаление теневых копий и массовое
создание файлов. Реакция автоматическая: за время ручного разбора
шифруется файловый сервер целиком.

**100500–100532, следы атаки на pdc-hv0.** 01.07.2026 на гипервизоре
отработал шифровальщик: запущен в 02:34 из `C:\PerfLogs\ded`,
остановлен в 03:41. За месяц до этого, 01.06.2026, в `C:\Windows`
появилась служба удалённого исполнения `winexesvc.exe` — и ни одно
правило её не ловило. Набор 100500–100532 закрывает всю
последовательность; самое раннее срабатывание — регистрация службы,
уровень 15, то есть месяц запаса вместо минут. Полный разбор отчёта
сканирования, включая то, что правила по-прежнему не увидят, —
`docs/16-incident-pdc-hv0.md`.

**100343, порог агента увольнений.** Агент обработки заявок на
увольнение (репозиторий `zayavka-rm`, каталог `dismissal-agent/`)
отключает учётные записи по заявкам. Шесть и более
отключений за час — либо ошибка в разборе заявок, либо чужие руки.

### Как добавить правило

```bash
# 1. Понять, что видит Wazuh
ssh ansible@10.5.2.85
sudo /var/ossec/bin/wazuh-logtest
# вставить строку журнала, посмотреть поля и сработавшее правило

# 2. Добавить правило в нужный файл
$EDITOR rules/ahp_infrastructure_rules.xml

# 3. Добавить образец в самопроверку
$EDITOR ansible/roles/wazuh_manager/defaults/main.yml
#    wazuh_rule_selftest_cases:

# 4. Раскатать
cd ansible && ansible-playbook site.yml --tags content --ask-vault-pass
```

Шаг 3 не формальность. Правило с опечаткой в регулярном выражении
молчит и выглядит ровно так же, как правило, для которого просто не
было событий. Самопроверка ловит это за секунды при раскатке, а не
через полгода при разборе инцидента.

### Регулярные выражения: подводный камень

В движке OS_Regex, который Wazuh использует по умолчанию:

* `.` — обычная точка, а `\.` — **любой символ** (обратно PCRE);
* квадратных скобок `[0-9]` нет;
* группировка с чередованием `(a|b)` работает не так, как ожидается.

Поэтому во всех нетривиальных выражениях явно указан `type="pcre2"`:

```xml
<field name="win.system.eventID" type="pcre2">^(55|140)$</field>
```

Правило без `type="pcre2"` и с группировкой — почти наверняка ошибка.

### Списки CDB

`ahp-privileged-users` работает в обе стороны: правило 100305
срабатывает на вход **из** списка (привилегированная запись зашла на
рабочую станцию), а 100020 и 100330 — на действие **вне** списка.
Добавляя служебную учётную запись, надо понимать: она перестанет
попадать под одни правила и начнёт попадать под другие.

Формат и сборка — `rules/lists/README.md`.

## Активное реагирование

### Что настроено

| Действие | Срабатывает | Где выполняется | Срок |
|----------|-------------|-----------------|------|
| Блокировка адреса | подбор паролей, сканирование, веб-атаки | на атакуемом узле | 30 мин, при повторах до 8 ч |
| Изоляция станции | вредоносное ПО, шифровальщик (100310–100312) | на самой станции | 1 час |
| Блокировка учётной записи AD | компрометация (100330–100331) | на контроллере домена | до ручного возврата |

### Предохранители

Автоматическое реагирование опаснее большинства атак, от которых оно
защищает. Поэтому предохранителей больше, чем самой логики.

**Список неблокируемых адресов.** `/var/ossec/etc/lists/ar-never-block.txt`
собирается Ansible из `wazuh_ar_never_block`. Туда входят контроллеры
домена, гипервизор, балансировщики, узлы портала, СУБД, сервер копий и
весь сегмент мониторинга. Скрипт блокировки проверяет принадлежность
адреса этим сетям целочисленной арифметикой, без внешних зависимостей.
Дополнительно и независимо от списка не блокируется шлюз по умолчанию.

Срабатывание защиты само становится событием: правило 100043,
результат `skipped-allowlist`. Это повод разобраться — либо правило
слишком широкое, либо атака идёт изнутри доверенной сети.

**Изоляция только рабочих станций.** Скрипт проверяет `ProductType`
Windows и отказывается изолировать сервер или контроллер домена.
Изоляция контроллера домена останавливает работу всей компании — это
дороже любого вредоноса на одной машине.

При изоляции остаются разрешены менеджеры Wazuh и контроллеры домена:
без первых машину нельзя будет разблокировать удалённо, без вторых
после перезагрузки никто не войдёт под доменной учётной записью,
включая администратора, который приедет разбираться.

**Блокировка учётных записей — самое ограниченное действие:**

* защищённые группы (администраторы домена, предприятия, схемы,
  операторы) не блокируются никогда — только сообщение и эскалация;
* точечный список неприкасаемых записей: `krbtgt`, служебные `svc_*`,
  `zabbix`, `bitrix`;
* не более трёх блокировок в час — превышение означает либо ошибку в
  правиле, либо атаку, рассчитанную на массовую блокировку сотрудников
  как способ остановить работу компании;
* состав групп и состояние записи сохраняются в JSON до изменения,
  поэтому возврат возможен;
* автоматической разблокировки нет: возврат доступа — решение человека.

Набор защищённых групп намеренно совпадает с агентом увольнений
(`zayavka-rm`, файл `dismissal-agent/config.psd1.example`). Два
инструмента трогают одну и
ту же службу каталога, и расхождение означало бы, что один разрешает
то, что запрещает другой.

### Возврат в рабочее состояние

Снять изоляцию со станции раньше срока:

```powershell
# локально на машине или через консоль ВМ на pdc-hv0
powershell -ExecutionPolicy Bypass -File \\10.2.27.118\wazuh$\ahp-unisolate-host.ps1
```

Скрипт удаляет только правила с префиксом `WAZUH-ISOLATION`, возвращает
политику межсетевого экрана и проверяет связь с менеджерами.

Разблокировать учётную запись:

```powershell
Enable-ADAccount -Identity ivanov
# состояние до блокировки:
Get-Content 'C:\Program Files\ossec-agent\active-response\ahp-state\ivanov_*.json'
```

Снять блокировку адреса вручную:

```bash
nft -a list chain inet wazuh input     # найти handle
nft delete rule inet wazuh input handle <N>
```

### Проверка реагирования

```bash
# подбор пароля с тестовой машины
for i in $(seq 1 8); do ssh неверный@10.0.1.220; done

# на атакованном узле
sudo nft list chain inet wazuh input
sudo grep ahp-ar /var/ossec/logs/active-responses.log
```

Ожидаемая запись:

```
2026/08/09 12:00:01 ahp-ar: action=block target=203.0.113.10 rule=100010 result=ok
```

## Журналы приложений: формат для собственных систем

Декодеры разбирают строки вида «ключ=значение», разделённые пробелом.
Такой формат надёжно разбирается движком Wazuh и читается человеком.

Что должны писать наши приложения:

```
zayavka: request=REQ-2026-0042 user=ivanov ip=10.0.1.55 action=create result=denied
sdp-sync: status=200 requests=14 errors=0
dismissal-agent: request=12345 user=ivanov action=disable result=ok
wazuh-backup: job=config target=gdrive status=ok size=482M
ahp-ar: action=block target=10.0.5.17 rule=100120 result=ok
```

Для `zayavka.php` это одна строка в обработчике:

```php
openlog('zayavka', LOG_PID, LOG_LOCAL0);
syslog(LOG_INFO, sprintf(
    'zayavka: request=%s user=%s ip=%s action=%s result=%s',
    $requestId, $login, $_SERVER['REMOTE_ADDR'], $action, $result
));
```

Значения не должны содержать пробелов — иначе разбор поля закончится
раньше. Если пробел неизбежен, заменять на подчёркивание.
