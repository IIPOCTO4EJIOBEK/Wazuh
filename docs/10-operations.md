# 10. Эксплуатация

## Регламент

### Ежедневно (10–15 минут)

- Открыть дашборд «AH Prostory — обзор SOC», период сутки.
- Разобрать инциденты уровня 12+ — по каждому должна быть заявка в SDP.
- Проверить, что поток событий не проваливался. Провал при неизменном
  числе агентов означает потерю событий, а не спокойный день.
- Посмотреть панель реагирования: что заблокировано за сутки и не
  сработала ли защита от блокировки своей же инфраструктуры.

### Еженедельно (30 минут)

```bash
cd wazuh-deploy/scripts
./healthcheck.sh
```

- Разобрать предупреждения.
- Проверить агентов в состоянии `disconnected` — либо машина выключена,
  либо агент сломан, либо машины уже нет и её надо снять с учёта.
- Посмотреть верхние строки «самых частых срабатываний»: правило,
  висящее там неделями, либо надо настраивать, либо устранять причину.

### Ежемесячно (2 часа)

- Отчёт по уязвимостям, сопоставить с планом обновлений.
- Проверить заполнение дисков индексера — расчёт в
  [02-sizing.md](02-sizing.md) не заменяет наблюдения.
- Проверить срок действия сертификатов:

```bash
for f in ansible/files/wazuh-certificates/*.pem; do
    echo "$(basename "$f"): $(openssl x509 -enddate -noout -in "$f")"
done
```

- Снять с учёта списанные машины.

### Ежеквартально (полдня)

- Учения по отказоустойчивости: `./failover-test.sh --all`
- Проверка восстановления из копии (см. [05-backup-restore.md](05-backup-restore.md)).
- Пересмотр правил: что срабатывало впустую, чего не хватило при
  разборе инцидентов.
- Обновление Wazuh, если вышла новая версия ветки.

## Обновление платформы

Версии пакетов закреплены, поэтому обычный `apt upgrade` кластер не
тронет. Обновление всегда осознанное.

```bash
# 1. Прочитать примечания к выпуску
# 2. Поменять версию
$EDITOR ansible/group_vars/all.yml    # wazuh_version

# 3. Снять закрепление и обновить по одному узлу,
#    порядок: индексер → менеджеры → дашборды
ansible-playbook site.yml --tags indexer --limit wazuh-idx-01 -e wazuh_pin_packages=false --ask-vault-pass
# дождаться green, затем следующий узел
```

Подробный порядок с запретом перебалансировки — в
[04-ha-failover.md](04-ha-failover.md), раздел «Обновление без простоя».

Агенты обновляются после сервера и **никогда раньше**: агент версии
новее менеджера не поддерживается. Порядок — сначала тестовая группа,
через неделю остальные.

## Изменение конфигурации

Единственный правильный способ — через репозиторий и Ansible.

```bash
$EDITOR ansible/group_vars/all.yml
cd ansible
ansible-playbook site.yml --check --diff --ask-vault-pass   # посмотреть, что изменится
ansible-playbook site.yml --tags manager --ask-vault-pass   # применить
git commit -am "Описание изменения"
```

Правка файла прямо на узле работает ровно до следующего прогона
Ansible, после чего молча пропадает. Обнаружить такое расхождение:

```bash
ansible-playbook site.yml --check --diff --ask-vault-pass
```

Изменения в `/var/ossec/etc` на менеджере, кроме того, поднимают
правило 100001 — то есть попадают в SIEM как событие безопасности.

## Смена паролей

```bash
# 1. Новые значения
ansible-vault edit group_vars/vault.yml

# 2. Индексер
ansible-playbook site.yml --tags indexer,indexer-init --ask-vault-pass

# 3. Менеджеры (API и filebeat)
ansible-playbook site.yml --tags manager --ask-vault-pass

# 4. Дашборды
ansible-playbook site.yml --tags dashboard --ask-vault-pass
```

Порядок обязателен: дашборд, обновлённый раньше индексера, потеряет
доступ и будет показывать пустой экран.

Пароль регистрации агентов меняется отдельно и требует внимания:
уже зарегистрированные агенты продолжат работать (у них свои ключи), но
файл на сетевом ресурсе `\\10.2.27.118\wazuh$\authd.pass` тоже надо
обновить, иначе новые машины не зарегистрируются.

## Перевыпуск сертификатов

Плановый — за месяц до истечения (узловые действуют 5 лет, корневой 10).

```bash
cd ansible
ansible-playbook playbooks/certificates.yml -e certs_force_regenerate=true --ask-vault-pass

# затем перезапуск в порядке: индексер (по одному) → filebeat → дашборд
ansible-playbook site.yml --tags indexer --ask-vault-pass
ansible-playbook site.yml --tags manager --ask-vault-pass
ansible-playbook site.yml --tags dashboard --ask-vault-pass
```

При добавлении узла достаточно прогнать плейбук сертификатов без
`certs_force_regenerate`: новому узлу выпустится сертификат, остальные
не тронутся. Для этого нужен корневой ключ — поэтому его и надо хранить.

## Права доступа

| Роль | Учётная запись | Что может |
|------|----------------|-----------|
| Администратор платформы | `admin` | всё, включая `securityadmin.sh` |
| Аналитик | именная, роль `wazuh_reader` | чтение алертов и дашбордов |
| Аудитор | `auditor` | то же, только чтение |
| Дежурный | именная, роль `wazuh_reader` | чтение |

Под `admin` в интерфейсе не работать. Аудит обращений к индексеру
включён, и в журнале должно быть видно, кто именно смотрел данные — а
не «admin».

Создание именной записи:

```bash
curl -k -u admin -X PUT \
  'https://10.5.2.81:9200/_plugins/_security/api/internalusers/petrov' \
  -H 'Content-Type: application/json' \
  -d '{"password":"...","backend_roles":["wazuh_reader"]}'
```

## Соответствие требованиям

Установка помогает закрыть часть требований, но не закрывает их сама
по себе. Что даёт платформа:

| Требование | Чем закрывается |
|-----------|-----------------|
| Регистрация событий безопасности (152-ФЗ, приказ ФСТЭК 21, РСБ.1–РСБ.7) | сбор журналов со всех узлов, хранение 400 суток |
| Защита журналов от изменения (РСБ.3) | журналы уезжают с узла в течение секунд; правки конфигурации менеджера — событие 100001 |
| Контроль целостности (ОЦЛ.1) | syscheck на системных каталогах и коде портала |
| Обнаружение вторжений (СОВ.1, СОВ.2) | правила обнаружения, MITRE ATT&CK |
| Анализ защищённости (АНЗ.1, АНЗ.2) | модуль уязвимостей, проверка конфигурации по CIS |
| Реагирование на инциденты (ИНЦ.1–ИНЦ.5) | заявки в ServiceDesk Plus, active response, журнал реагирования |
| PCI DSS 10.x | те же журналы, хранение свыше года |

Чего платформа не делает и что остаётся организационной работой:
классификация информационных систем, модель угроз, регламент
реагирования на бумаге, обучение персонала, аттестация. SIEM даёт
техническую основу для этих документов, а не заменяет их.

Полезно знать при проверке: срок хранения 400 суток выбран так, чтобы
годовой цикл проверок видел весь предыдущий год целиком.

## Полезные команды

```bash
# Состояние служб менеджера
/var/ossec/bin/wazuh-control status

# Кластер менеджеров
/var/ossec/bin/cluster_control -l
/var/ossec/bin/cluster_control -a      # какие файлы синхронизированы

# Агенты
/var/ossec/bin/agent_control -l
/var/ossec/bin/agent_control -i 042    # подробности по агенту

# Проверка конфигурации перед перезапуском
/var/ossec/bin/wazuh-analysisd -t
/var/ossec/bin/verify-agent-conf

# Разбор события правилами
/var/ossec/bin/wazuh-logtest

# Очереди и нагрузка
cat /var/ossec/var/run/wazuh-analysisd.state
cat /var/ossec/var/run/wazuh-remoted.state

# Индексер
curl -k -u admin 'https://10.5.2.81:9200/_cat/nodes?v'
curl -k -u admin 'https://10.5.2.81:9200/_cat/indices/wazuh-*?v&s=index'
curl -k -u admin 'https://10.5.2.81:9200/_cat/allocation?v'

# Балансировщик
curl -s http://10.5.2.92:8404/stats
```
