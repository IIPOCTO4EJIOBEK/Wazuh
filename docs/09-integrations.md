# 09. Интеграции

Оповещение построено на трёх каналах с разным назначением. Дублирование
здесь осознанное: у каналов разная надёжность и разное время реакции.

| Канал | Порог | Что даёт | Чего не даёт |
|-------|-------|----------|--------------|
| ServiceDesk Plus | уровень 12+ | учёт, владелец, срок | скорости — заявку могут увидеть через час |
| Telegram | уровень 10+ | скорость — минуты | учёта, сообщение теряется в чате |
| Zabbix | уровень 10+ и метрики платформы | эскалацию по расписанию дежурств | подробностей события |
| Почта | уровень 10+ | привычный канал, работает всегда | и того, и другого |

---

## ServiceDesk Plus

Инцидент, оформленный письмом, не имеет ни владельца, ни срока, и
теряется вместе с письмом. В компании уже работает ServiceDesk Plus
(support.uk-n.ru) с учётом работ и сроками реакции — инциденты
безопасности должны попадать туда же.

### Что настроено

`/var/ossec/integrations/custom-servicedesk.py` создаёт заявку:

* тема: `[Wazuh <уровень>] <описание правила> — <узел>`;
* описание: правило, узел, время, источник, учётная запись, техники
  MITRE, исходное событие, ссылка на дашборд;
* приоритет по уровню: 15 → критический, 13–14 → высокий, 12 → средний;
* группа исполнителей: «Служба технической поддержки»;
* категория: «Информационная безопасность».

### Подавление повторов

Одинаковые алерты (одно правило + один узел) в течение часа не создают
новую заявку, а дописываются комментарием к уже открытой.

Без этого одна атака перебором создаёт сотню заявок и хоронит очередь
поддержки — а вместе с ней и все остальные заявки, включая те, что не
про безопасность.

Окно подавления считается от первой заявки, а не от последнего события:
иначе непрерывная атака никогда не создала бы вторую заявку, и через
час после начала инцидент выглядел бы закрытым.

### Настройка

Токен технического пользователя SDP кладётся в `vault.yml`:

```yaml
vault_servicedesk_authtoken: "..."
```

Пользователю нужны права: создание заявок, добавление комментариев,
чтение шаблона «Инцидент информационной безопасности».

Порог задаётся в `group_vars/all.yml`:

```yaml
alert_level_servicedesk: 12
```

### Проверка

```bash
cat > /tmp/alert.json <<'JSON'
{"timestamp":"2026-08-09T12:00:00.000+0300",
 "rule":{"id":"100311","level":15,"description":"Проверка интеграции","groups":["ahp"]},
 "agent":{"id":"001","name":"test-host","ip":"10.0.0.1"},
 "manager":{"name":"wazuh-mgr-01"},
 "data":{"srcip":"10.0.0.1"},
 "full_log":"проверка интеграции ServiceDesk Plus"}
JSON

/var/ossec/integrations/custom-servicedesk /tmp/alert.json
tail -5 /var/ossec/logs/integrations.log
```

В журнале должна появиться строка «создана заявка N».

## Zabbix

Отказ SIEM не может быть замечен самой SIEM. Поэтому состояние
платформы контролируется извне — тем самым Zabbix (10.5.2.74), где уже
настроены эскалации и расписание дежурств.

### Метрики

Скрипт `/usr/local/sbin/wazuh-zabbix-report.sh` раз в пять минут
отправляет по протоколу trapper:

| Ключ | Что |
|------|-----|
| `wazuh.api.available` | 1/0 |
| `wazuh.agents.active/disconnected/never_connected/total` | сводка по агентам |
| `wazuh.cluster.nodes` | узлов в кластере менеджеров |
| `wazuh.indexer.status` | 0 green, 1 yellow, 2 red, 3 недоступен |
| `wazuh.indexer.number_of_nodes/active_shards/unassigned_shards` | состояние кластера |
| `wazuh.analysisd.events_processed/events_dropped` | поток событий |
| `wazuh.analysisd.event_queue_usage` | заполнение очереди |
| `wazuh.snapshot.age_hours` | часов с последнего снапшота |
| `wazuh.alert` | текст последнего инцидента уровня 10+ |

### Установка шаблона

1. Zabbix → Настройка → Шаблоны → Импорт →
   `integrations/zabbix/wazuh_template.yaml`
2. Создать узел с именем `wazuh-cluster` (совпадает с `ZABBIX_HOST` в
   `/var/ossec/etc/integrations.env`), привязать шаблон.
3. Разрешить менеджерам подключение к 10.5.2.74:10051.

Одиннадцать триггеров, из них три уровня «катастрофа»: индексер в
состоянии red, индексер недоступен, API недоступен.

Отдельно стоит триггер «поток событий прекратился»: менеджер жив, API
отвечает, а счётчик обработанных событий не растёт. Это то состояние,
которое из самой Wazuh выглядит как спокойный день.

### Проверка

```bash
/usr/local/sbin/wazuh-zabbix-report.sh
zabbix_get -s 10.5.2.74 -k wazuh.indexer.status    # с сервера Zabbix
```

## Telegram

Быстрый канал: заявка фиксирует инцидент, а сообщение сокращает время
до первого взгляда человека.

Выключен по умолчанию — включается после выдачи бота:

```yaml
# group_vars/all.yml
telegram_enabled: true

# vault.yml
vault_telegram_bot_token: "..."
vault_telegram_chat_id: "-100..."
```

Ограничение — не более 12 сообщений за 5 минут. Чат, в который за
минуту прилетело двести сообщений, дежурный выключает, и дальше он не
видит ничего.

smtp_enabled: true

smtp_from: "wazuh@ahprostory.ru"
smtp_to:
  - "it-security@ahprostory.ru"

Ограничение — 24 письма в час (`email_maxperhour`), дальше события
группируются.

## Добавление своей интеграции

1. Написать `integrations/custom-<имя>.py` — на вход путь к файлу с
   алертом первым аргументом.
2. Скопировать обёртку: `cp custom-telegram custom-<имя>`.
3. Добавить файлы в список в
   `ansible/roles/wazuh_integrations/tasks/main.yml`.
4. Добавить блок в `ossec.conf.j2`:

```xml
<integration>
  <name>custom-имя</name>
  <hook_url>...</hook_url>
  <level>12</level>
  <alert_format>json</alert_format>
</integration>
```

Что учесть в любом сценарии интеграции:

* **ограничение частоты** — иначе шторм алертов превращается в шторм
  сообщений, и канал перестают читать;
* **таймауты на все сетевые вызовы** — зависшая интеграция подвешивает
  `wazuh-integratord`, и следом перестают уходить все остальные
  оповещения;
* **журналирование в `/var/ossec/logs/integrations.log`** — иначе
  молчащая интеграция неотличима от отсутствия событий;
* **не падать при недоступности получателя** — потеря сообщения хуже,
  чем потеря всей очереди оповещений.

Все три готовых сценария написаны на стандартной библиотеке Python без
внешних зависимостей: интеграция не должна ломаться от обновления
пакетов на менеджере.
