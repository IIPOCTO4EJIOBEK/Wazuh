# 16. Разбор сканирования pdc-hv0 от 01.07.2026

Отчёт THOR по гипервизору pdc-hv0. Разбор понадобился не ради самого
отчёта: он показывает, какие события Wazuh должен был бы поднять и
чего в наборе правил не было. Всё, что дописано по итогам, собрано в
`rules/ahp_ioc_rules.xml` (диапазон 100500–100599).

---

## Что за отчёт

| | |
|---|---|
| Сканер | THOR Lite 10.7.30 |
| База сигнатур | 1.260429.95919 |
| Узел | pdc-hv0, Windows Server 2022 Datacenter |
| Адрес в отчёте | 10.1.10.50 |
| Запущен от | `PDC-HV0\vardo001`, с правами администратора |
| Время | 01.07.2026, 12:37–12:51 |
| Итог | 0 предупреждений высшего уровня, 2 предупреждения, 51 замечание |

**«0 Alerts» здесь ничего не значит.** Это классификация сканера по
внутренней шкале, а не заключение о чистоте узла. Файл со счётом 81 из
100 и совпадением по правилу YARA попал в категорию Warning — и это
самая тяжёлая находка отчёта.

Ограничения, которые надо держать в голове при чтении:

* редакция Lite — часть модулей отключена, сканирование по правилам
  Sigma недоступно;
* база сигнатур старше 60 дней, о чём сканер сам предупреждает первой
  строкой;
* сканирование однократное, по состоянию файловой системы на 12:37
  01.07.2026.

## Находки

### 1. Служба удалённого исполнения

```
C:\Windows\winexesvc.exe
SHA256   65f8ccfbfbab07e0ac50cc27e133841a170ea1e9edbbc65ee2cd6addbb0994d1
MD5      cee3545e6bd5571f22ee858c65745d69
создан   01.06.2026 22:22:57
изменён  10.06.2026 17:01:21
счёт     81 (YARA Winexe_RemoteExec + совпадение по имени файла)
```

Это серверная часть `winexe` — средство запуска команд на удалённом
узле по SMB. Работает так же, как PsExec: файл копируется на узел,
регистрируется как служба, команды принимаются через именованный канал.
В теле файла сканер нашёл строку `\\.\pipe\ahexec` — это канал по
умолчанию, то есть сборка не переименована.

Легитимного применения на серверах компании у него нет: удалённое
управление идёт через RDP и WinRM.

Дата важнее самого файла. **Он появился 1 июня, за месяц до
шифрования.** Это был месяц, в течение которого происходящее можно было
заметить и остановить.

### 2. Шифровальщик

```
C:\PerfLogs\ded\svhost.exe.[DEBUG].sys   8672 байта   создан 01.07.2026 02:34:09
C:\PerfLogs\ded\svhost.exe.[INFO].sys    3812 байта   создан 01.07.2026 02:34:09
                                                      изменён 01.07.2026 03:40:45
```

Это не исполняемые файлы, несмотря на расширение `.sys`. Первые байты —
UTF-16LE, текст начинается с `~~~~~ CRYP`. Это собственные журналы
работы программы `svhost.exe` — подделка под системный `svchost.exe` с
пропущенной буквой.

**Самого `svhost.exe` на диске уже не было.** Сканер видит только его
журналы и упоминания в чужих. Значит, хеша основного файла у нас нет, и
проверка по хешу его не поймает.

### 3. Что он делал

Из журнала Microsoft Defender
(`MPLog-20260425-172246.log`) — 45 записей, все от процесса
`\PerfLogs\ded\svhost.exe` с идентификатором 9048:

```
2026-06-30T23:34:09.469 [RTP] [Mini-filter] Denied access to file
  [\Program Files\Windows Defender\AmMonitoringInstall.mof]
  from process [\Device\HarddiskVolume17\PerfLogs\ded\svhost.exe][Pid:9048]
  on Post-Create. Reason: FsHardening.
```

и, что важнее:

```
Denied access to file [\Program Files\Windows Defender\RECOVER-VPmwmJiwz-FILES.txt]
  ... on Pre-Create. Reason: FsHardening.
Denied access to file [\Program Files (x86)\Windows Defender\RECOVER-VPmwmJiwz-FILES.txt]
Denied access to file [\Program Files\Windows Defender\Platform\RECOVER-VPmwmJiwz-FILES.txt]
```

Отметка `2026-06-30T23:34:09` — это UTC. Defender пишет время в UTC,
Veeam и файловая система — по местному времени, и та же секунда там
выглядит как `01.07.2026 02:34:09`. Разница в три часа между записями
об одном и том же событии — не расхождение, а разные часовые пояса в
журналах. Сам сканер тоже помечает события временем UTC: находки
датированы `Jul 1 09:44`, тогда как сканирование шло с 12:37 по
местному.

`RECOVER-…-FILES.txt` — записка вымогателя. Программа обходила каталоги
и в каждом пыталась её оставить. В каталогах самого Defender не вышло:
их закрывает механизм FsHardening. **Из этого не следует, что не вышло
где-то ещё** — отчёт показывает только те каталоги, куда Defender не
пустил.

Время запуска и остановки — из журнала драйвера Veeam:

```
[01.07.2026 02:34:09.172] VS_PS: process creation: 2358, parent = 4bec,
    image filename: "\Device\HarddiskVolume17\PerfLogs\ded\svhost.exe"
[01.07.2026 03:40:51.280] VS_PS: process termination: 2358
```

## Чего отчёт не говорит

Перечень важен не меньше самих находок — на эти вопросы отвечают
другие источники, и если их нет, ответа не будет вообще.

**Кто запустил `svhost.exe`.** В журнале Veeam указан родительский
процесс `4bec`, но его имени там нет. Ответ дало бы событие 4688 журнала
Security с полем родительского процесса — если аудит запуска процессов
включён и события собираются.

**Как попал `winexesvc.exe`.** Служба ставится с чужого узла под учётной
записью администратора. Какой именно и откуда — видно по событиям входа
4624 с типом 3 и по событию регистрации службы 7045.

**Что зашифровано.** Отчёт перечисляет только каталоги, куда программу
не пустил Defender. Объём ущерба по нему не оценивается.

**Осталось ли закрепление.** Однократное сканирование состояния
файловой системы. Задания планировщика, автозапуск, службы, учётные
записи, созданные за этот месяц, — отдельная проверка.

**Расхождение по адресу.** В отчёте pdc-hv0 значится как `10.1.10.50`, в
инвентаре проекта (`ansible/inventory/hosts.yml`) — как `10.2.27.118`.
Либо у узла несколько интерфейсов, либо инвентарь устарел. Сверить
нужно до подключения агента: иначе агент встанет не на тот узел.

## Что из этого увидел бы Wazuh

Честный разбор по каждой находке. «Было» — набор правил до этого
разбора, «стало» — с учётом `ahp_ioc_rules.xml`.

| Событие | Было | Стало |
|---------|------|-------|
| Появление `winexesvc.exe` в `C:\Windows` | ничего: каталог не наблюдался | 100523, уровень 13 — контроль целостности корня `%WINDIR%` |
| Регистрация службы `winexesvc` (7045) | ничего | 100510, уровень 15 — изоляция узла |
| Запуск `winexesvc.exe` (4688) | ничего: 100314 знает psexec, но не winexe | 100502, уровень 15 |
| Запуск `svhost.exe` из `C:\PerfLogs` (4688) | ничего | 100500, уровень 13 |
| Появление файлов в `C:\PerfLogs` | ничего: каталог не наблюдался | 100521, уровень 13 |
| Записка `RECOVER-…-FILES.txt` | ничего | 100520, уровень 15 — **только в наблюдаемых каталогах** |
| Отказы Defender FsHardening | ничего | ничего: MPLog в журнал событий не попадает |
| Массовое шифрование файлов ВМ | ничего | ничего: хранилище ВМ под контроль целостности не берётся |

Два «ничего» в правой колонке — не недоработка, а сознательный выбор,
и о нём лучше знать заранее.

`MPLog` — текстовый журнал Defender на диске. Читать его агентом
технически можно (`localfile` с `log_format` `syslog`), но он в UTF-16,
растёт на десятки мегабайт в сутки и состоит почти целиком из
служебных записей. Наблюдаемая часть работы Defender — события
журнала: 1116/1117 (правило 100310), 5001/5010/5012/5013 (100530),
1121/1126 (100532).

Хранилище виртуальных машин — десятки терабайт постоянно меняющихся
файлов. Контроль целостности по ним стоил бы дороже пользы. Массовое
шифрование на гипервизоре ловится не по файлам, а по запуску процесса
и по записке вымогателя в системных каталогах.

**Главный вывод.** Самое раннее надёжное срабатывание — регистрация
службы 1 июня, уровень 15, с автоматической изоляцией узла. Не
предупреждение за минуты до шифрования, а месяц запаса.

## Что делать с узлом

Порядок, а не список: каждый следующий шаг опирается на предыдущий.

**1. Не выключать и не переустанавливать сразу.** Пока узел в текущем
состоянии, с него снимаются журналы. После переустановки не останется
ничего.

**2. Снять копии журналов до ротации.**

```powershell
$dst = "D:\ir-pdc-hv0-20260701"
New-Item -ItemType Directory -Force -Path $dst | Out-Null

# Журналы событий целиком
wevtutil epl Security "$dst\Security.evtx"
wevtutil epl System   "$dst\System.evtx"
wevtutil epl Application "$dst\Application.evtx"
wevtutil epl "Microsoft-Windows-PowerShell/Operational" "$dst\PowerShell.evtx"
wevtutil epl "Microsoft-Windows-TerminalServices-LocalSessionManager/Operational" `
             "$dst\TerminalServices.evtx"

# Журналы Defender и Veeam, на которых построен разбор
Copy-Item "C:\ProgramData\Microsoft\Windows Defender\Support\MPLog-*.log" $dst
Copy-Item "C:\ProgramData\Veeam\Backup\Driver.VeeamFCT.log" $dst

# Собственные журналы шифровальщика
Copy-Item "C:\PerfLogs\ded\*" $dst -Recurse
```

**3. Ответить на вопрос, кто запустил.**

```powershell
# Родительский процесс запуска svhost.exe
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4688;
    StartTime=[datetime]'2026-07-01 02:30'; EndTime=[datetime]'2026-07-01 02:40'} |
  Where-Object { $_.Message -match 'svhost|PerfLogs' } | Format-List

# Регистрация службы winexesvc
Get-WinEvent -FilterHashtable @{LogName='System'; Id=7045;
    StartTime=[datetime]'2026-06-01'; EndTime=[datetime]'2026-06-11'} | Format-List

# Сетевые входы в ночь на 1 июля
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624;
    StartTime=[datetime]'2026-06-30 20:00'; EndTime=[datetime]'2026-07-01 06:00'} |
  Where-Object { $_.Message -match 'Logon Type:\s+3' } | Format-List
```

Если событий 4688 нет — аудит запуска процессов не был включён. Это
само по себе ответ: включать нужно сейчас, скрипт
`scripts/pilot/Enable-AdAuditPolicy.ps1`.

**4. Убрать закрепление.**

```powershell
Stop-Service winexesvc -ErrorAction SilentlyContinue
sc.exe delete winexesvc
# Файл — в карантин, не удалять: он нужен для разбора
Move-Item C:\Windows\winexesvc.exe $dst\winexesvc.exe.quarantine
```

**5. Проверить, где ещё то же самое.** `winexe` расходится по сети, и
один узел — почти наверняка не единственный.

```powershell
# По всем узлам домена: наличие файла и службы
$hosts = Get-ADComputer -Filter {OperatingSystem -like "*Server*"} |
         Select-Object -ExpandProperty DNSHostName
Invoke-Command -ComputerName $hosts -ErrorAction SilentlyContinue -ScriptBlock {
    [pscustomobject]@{
        Host    = $env:COMPUTERNAME
        Winexe  = Test-Path C:\Windows\winexesvc.exe
        Service = [bool](Get-Service winexesvc -ErrorAction SilentlyContinue)
        PerfLog = @(Get-ChildItem C:\PerfLogs -Recurse -ErrorAction SilentlyContinue).Count
    }
} | Format-Table
```

**6. Сменить пароли учётных записей с правами администратора на
узле.** Запуск службы удалённого исполнения означает, что учётные
данные администратора у атакующего были. Пароли, действовавшие с 1 июня,
считаются известными.

**7. Проверить резервные копии.** Шифровальщики целенаправленно портят
их первыми. Восстановление нужно проверить фактическим
восстановлением одной машины, а не отметкой «задание выполнено» в
консоли.

**8. Поставить агента Wazuh на узел.** Это то, что закрывает вопрос
на будущее: повторение той же последовательности поднимет тревогу
пятнадцатого уровня в момент регистрации службы. Установка —
`docs/06-agents.md`, группы `default,windows,hyperv`.

## О ложных срабатываниях новых правил

Два правила из набора шумят по-разному, и лучше знать это заранее.

**100523, исполняемый файл в корне `C:\Windows`.** Ежемесячные
обновления системы заменяют `explorer.exe` и несколько библиотек —
правило сработает. Раз в месяц, предсказуемо, по известному имени
файла. Оставлено уровнем 13 сознательно: событие редкое, а глушить
именно этот канал означает вернуться к состоянию, в котором
`winexesvc.exe` пролежал незамеченным месяц.

**100511 и 100512, служба из служебного каталога.** Часть установщиков
регистрирует временные службы из `C:\Users\…\AppData\Local\Temp`. Если
такое найдётся, исключение заводится по конкретному имени службы в
`rules/ahp_tuning.xml`, а не снятием правила целиком.

Правила уровня 15 из этого набора запускают изоляцию узла. Для
гипервизора это означает потерю управления виртуальными машинами по
сети, поэтому перед включением автоматического действия на pdc-hv0
стоит договориться, что изоляция гипервизора допустима — либо внести
его в исключения active response и оставить только оповещение.
