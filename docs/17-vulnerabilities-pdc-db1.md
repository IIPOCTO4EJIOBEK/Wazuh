# 17. Уязвимости: разбор отчёта по PDC-DB1

Отчёт Wazuh по узлу PDC-DB1 от 20.08.2026 — первый развёрнутый набор
данных по уязвимостям с боевого сервера. Разобран здесь не ради самого
сервера: на нём видно, как читать эти числа и почему прямой их перенос
в план работ даёт неверный результат.

| | |
|---|---|
| Узел | PDC-DB1, 10.1.20.41 |
| ОС | Windows Server 2019 Standard, сборка 10.0.17763.6054 |
| Роль | Microsoft SQL Server 2019 |
| Агент | 013, Active, версия 4.14.7, группы `default,windows,mssql` |
| Инвентарь | свыше 8600 пакетов |
| Найдено уязвимостей | 1340: 18 критичных, 940 высоких, 371 средних, 11 низких |

---

## Первое: пилот работает

Второй узел после pbx1, на котором прошла полная цепочка — агент
зарегистрировался, собрал инвентарь, менеджер сопоставил его с базой и
выдал уязвимости. Это и есть приёмочный признак модуля.

## Второе: 1340 — это одна проблема, а не 1340

Разбивка по компонентам из отчёта:

| Компонент | Уязвимостей |
|-----------|-------------|
| Microsoft Windows Server 2019 Standard 10.0.17763.6054 | 1305 |
| Microsoft SQL Server 2019 Setup (English) | 17 |
| 7-Zip 22.01 (x64) | 14 |
| остальное | 4 |

**97% приходится на одну строку — сборку операционной системы.**
Сборка `17763.6054` соответствует накопительному обновлению за июль
2024 года. Отчёт — от августа 2026. То есть на сервере не установлено
порядка двадцати пяти ежемесячных накопительных обновлений подряд.

Отсюда практический вывод, который не виден из числа 1340: закрывается
это не работой по списку CVE, а одним накопительным обновлением с
перезагрузкой. Разбирать 940 высоких уязвимостей по отдельности не
нужно и вредно — время уйдёт на разбор, а сервер останется
необновлённым.

## Третье: числа завышены, и знать об этом важно

Модуль сопоставляет уязвимости **со сборкой системы, а не с набором
установленных ролей**. В списке двадцати пяти самых тяжёлых видно
прямо:

| CVE | Компонент | Установлен ли на сервере СУБД |
|-----|-----------|-------------------------------|
| CVE-2025-59287 | Windows Server Update Service | вряд ли |
| CVE-2026-45602 | DHCP Server | вряд ли |
| CVE-2024-38199 | Line Printer Daemon | вряд ли |
| CVE-2026-21255 | Hyper-V | вряд ли |
| CVE-2026-47289, CVE-2026-32157 | Remote Desktop **Client** | есть, но нужен исходящий сеанс |

Если роль не установлена, уязвимого кода на диске нет и достижимой
поверхности он не даёт. Проверяется одной командой:

```powershell
Get-WindowsFeature | Where-Object Installed | Select-Object Name, DisplayName
```

На выводы по срочности это не влияет — обновление закрывает и то и
другое разом. Но при разговоре с руководством разница между «18
критичных уязвимостей на сервере» и «18 совпадений по сборке, из
которых достижимы столько-то» существенная, и лучше называть вещи
своими именами самому, чем потом объясняться.

## Четвёртое: что действительно достижимо

Из критичных остаются те, которым не нужна отдельная роль и не нужна
учётная запись:

| CVE | CVSS | Что это |
|-----|------|---------|
| CVE-2026-47291 | 9.8 | переполнение в HTTP.sys, по сети без проверки подлинности. HTTP.sys есть на любом сервере и слушает, если работает WinRM (5985) или службы отчётов SQL |
| CVE-2025-47981 | 9.8 | переполнение в SPNEGO — согласование проверки подлинности, по сети без учётной записи |
| CVE-2024-38063 | 9.8 | стек TCP/IP, обработка IPv6 |
| CVE-2024-49112 | 9.8 | LDAP, важно рядом с контроллером домена (10.1.20.21 в той же подсети) |
| CVE-2026-41089, CVE-2024-38124 | 9.8 / 9.0 | Netlogon, там же |
| CVE-2026-44815 | 9.8 | клиент DHCP — работает всегда, если адрес получен по DHCP |

Отдельно — две записи, у которых в ссылках отчёта стоит каталог CISA
KEV, то есть их применение в атаках зафиксировано: **CVE-2025-59287**
(WSUS) и **CVE-2026-21513** (MSHTML). Такие обновляются вне очереди,
без обсуждения оценки CVSS.

## Пятое: чего в отчёте нет

**Уровень обновлений самого SQL Server.** В списке значится
`Microsoft SQL Server 2019 Setup (English)` — это запись установщика в
списке программ, а не движок. Фактическую сборку показывает сам сервер:

```sql
SELECT @@VERSION;
SELECT SERVERPROPERTY('ProductLevel'), SERVERPROPERTY('ProductUpdateLevel');
```

Для SQL Server 2019 актуальным считается последний накопительный пакет
CU; если там уровень RTM или ранний CU, это отдельная задача, и по
отчёту Wazuh она не видна.

**Проверка конфигурации по CIS.** На pbx1 модуль SCA дал оценку 41%, по
PDC-DB1 в отчёте её нет. Стоит посмотреть на вкладке узла: пароли,
права, параметры службы SQL часто дают больше, чем неустановленные
обновления.

**Достижимость по сети.** Ни один сканер уязвимостей не знает, кто
может дойти до порта 1433 и 5985 этого сервера. Это правила на
межсетевом экране, и смотреть их нужно отдельно.

## Порядок работ

**1. Снять точку возврата.** Сервер базы данных, обновление
двухлетней давности за один проход. До установки — проверенная
резервная копия баз и контрольная точка виртуальной машины.

**2. Установить накопительное обновление и перезагрузить.** Без
перезагрузки сборка не изменится, и повторный отчёт покажет то же
самое.

**3. Обновить 7-Zip.** Версия 22.01 вышла в 2022 году, 14 уязвимостей.
Работа на пять минут, отдельного окна обслуживания не требует.

**4. Пересобрать отчёт и сравнить.** Это единственная проверка
результата. Ожидание — три с половиной цифры вместо четырёх, и
критичных заметно меньше.

```bash
# Убедиться, что агент переслал обновлённый инвентарь
curl -sk -u admin \
  "https://10.17.1.252:9200/wazuh-states-vulnerabilities-*/_count" \
  -H 'Content-Type: application/json' \
  -d '{"query":{"bool":{"must":[
        {"term":{"agent.name":"pdc-db1"}},
        {"term":{"vulnerability.severity":"Critical"}}]}}}'
```

**5. Проверить уровень CU у SQL Server** — см. запрос выше.

**6. Закрепить процесс.** Разовое обновление отложит проблему на
месяц. Нужен график обслуживания: у сервера базы данных — окно раз в
месяц с перезагрузкой.

## Что из этого меняется в проекте

Отчёт вскрыл разрыв, который к самому PDC-DB1 отношения не имеет.
**Восемнадцать критичных уязвимостей на ключевом узле не подняли ни
одного события.** Данные лежали в индексе и ждали, пока человек
откроет вкладку. Единственным механизмом реагирования был пункт
«ежемесячно: отчёт по уязвимостям» в регламенте эксплуатации
([10-operations.md](10-operations.md)).

Добавлены правила 100480–100482 в
`rules/ahp_infrastructure_rules.xml`:

| Правило | Уровень | Когда |
|---------|--------:|-------|
| 100480 | 12 | критичная уязвимость на узле из списка `ahp-critical-hosts` — заявка в ServiceDesk Plus |
| 100481 | 7 | критичная уязвимость на любом другом узле — в дашборд |
| 100482 | 13 | уязвимость из каталога CISA KEV, то есть применяемая в атаках |

Разделение по важности узла сделано намеренно. Критичная уязвимость на
рабочей станции и на контроллере домена — разные события, и одинаковый
уровень для них означал бы либо шум, либо пропуск.

**Правила требуют проверки на стенде.** Они опираются на группу
`vulnerability-detector` и на имена полей события, а те зависят от
версии менеджера. Порядок проверки — в комментарии к правилам в самом
файле. Пока проверка не пройдена, считать, что оповещение по
уязвимостям работает, нельзя.
