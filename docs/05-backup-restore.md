# 05. Резервирование данных и восстановление

Резервируются три разные вещи, с разными сроками и разными способами
восстановления. Путать их нельзя: копия конфигурации без снапшота
индексов даёт работающую систему без истории, а снапшот без
конфигурации — историю без возможности принять агентов.

| Что | Где | Как часто | Хранится | Восстановление |
|-----|-----|-----------|----------|----------------|
| Индексы алертов | снапшоты OpenSearch на NFS | ежедневно 02:00 | 30 копий | `backup/restore-indices.sh` |
| Конфигурация менеджеров | tar.gz на узле + rclone | ежедневно 01:30 | 60 суток | `backup/wazuh-restore.sh` |
| Правила и код развёртывания | этот git-репозиторий | при каждом изменении | всегда | `git checkout` + Ansible |

---

## Показатели восстановления

| Сценарий | RPO (потеря данных) | RTO (время восстановления) |
|----------|--------------------|---------------------------|
| Отказ одного узла индексера | 0 | 0, работа не прерывается |
| Отказ одного менеджера | 0 | 0 |
| Потеря индекса за сутки | до 24 ч | 1–3 ч (зависит от объёма) |
| Полная потеря менеджера | 0 (конфигурация) | 1 ч |
| Полная потеря кластера индексера | до 24 ч | 4–8 ч |
| Потеря площадки | все исторические события | 1–2 суток на новом месте |

RPO в сутки для индексов — следствие ежедневного снапшота. Уменьшить
его можно, поставив снапшоты каждые 6 часов (`snapshot_schedule_cron`),
ценой нагрузки на хранилище в рабочее время.

## Снапшоты индексов

### Как устроено

Репозиторий — общий NFS-ресурс, смонтированный **на всех трёх узлах
индексера по одному и тому же пути** `/mnt/wazuh-snapshots`. Это
требование OpenSearch: снапшот пишут все узлы одновременно, каждый свою
часть шардов. Смонтировано на одном узле — снапшот не соберётся.

Плейбук проверяет это явно и падает, если репозиторий виден не всем
узлам.

Снапшоты инкрементальные: первый занимает объём всех индексов,
последующие — только изменения. Тридцать ежедневных копий при суточном
приросте около 6 ГБ занимают порядка 400–600 ГБ.

Расписание задаёт политика `wazuh-daily` (плагин Snapshot Management):
создание в 02:00, удаление старше 30 копий в 03:30.

### Проверка

```bash
# список снапшотов
curl -k -u admin 'https://10.5.2.81:9200/_cat/snapshots/wazuh-snapshots?v&s=start_epoch:desc'

# состояние политики
curl -k -u admin 'https://10.5.2.81:9200/_plugins/_sm/policies/wazuh-daily/_explain?pretty'
```

Свежесть последнего снапшота проверяется автоматически: `healthcheck.sh`,
скрипт резервного копирования и метрика `wazuh.snapshot.age_hours` в
Zabbix. Порог тревоги — 36 часов.

### Восстановление индексов

```bash
cd wazuh-deploy/backup

# что есть в репозитории
./restore-indices.sh --list

# восстановить под другим именем — так делают почти всегда
./restore-indices.sh --snapshot wazuh-daily-2026.08.05-02.00 \
                     --indices 'wazuh-alerts-4.x-2026.06*'

# перезаписать существующие индексы — только при реальной потере данных
./restore-indices.sh --snapshot wazuh-daily-2026.08.05-02.00 \
                     --indices 'wazuh-alerts-4.x-2026.08.09' --replace
```

Режим по умолчанию — `--rename`: данные поднимаются в индексы
`restored-*`, рабочие не затрагиваются. Для расследования это
правильный режим: оно не должно менять то, что расследуется.

Чтобы увидеть восстановленные данные в интерфейсе, создайте шаблон
индекса `restored-wazuh-alerts-*` с полем времени `timestamp`. После
расследования копию удалить:

```bash
curl -k -u admin -X DELETE 'https://10.5.2.81:9200/restored-*'
```

## Копии конфигурации менеджеров

### Что попадает в копию

| Путь | Почему это важно |
|------|------------------|
| `etc/client.keys` | без него восстановленный менеджер не примет ни одного агента — все 400 придётся регистрировать заново |
| `etc/ossec.conf`, `local_internal_options.conf` | настройка под нашу нагрузку |
| `etc/rules`, `etc/decoders`, `etc/lists` | правила обнаружения |
| `etc/shared` | конфигурации групп агентов |
| `etc/authd.pass` | пароль регистрации |
| `api/configuration` | пользователи и настройки Wazuh API |
| `active-response/bin` | скрипты реагирования |
| `queue/db` | состояние агентов и групп |

`client.keys` — самый ценный файл во всей установке: весит килобайты,
а его потеря стоит нескольких дней работы.

Базы состояния копируются через `sqlite3 .backup`, а не обычным `cp`:
файл, скопированный на ходу, может оказаться в несогласованном
состоянии, и это выяснится только при восстановлении.

Алерты в копию **не входят** — они в индексере, у них свои снапшоты.

### Ручной запуск

```bash
/usr/local/sbin/wazuh-backup.sh              # копия + выгрузка наружу
/usr/local/sbin/wazuh-backup.sh --dry-run    # проверка без изменений
```

Каждый запуск пишет строку в журнал в формате, который разбирает
декодер `wazuh-backup`. Неудачное копирование поднимает правило 100442,
две неудачи подряд — 100443 уровня 14 с заявкой в ServiceDesk Plus.
Резервное копирование, о поломке которого никто не узнаёт, бесполезно.

### Восстановление менеджера

```bash
# 1. Чистый узел, тот же адрес, та же версия Wazuh
ansible-playbook site.yml --tags manager --limit wazuh-mgr-01 --ask-vault-pass

# 2. Конфигурация из копии
/usr/local/sbin/wazuh-restore.sh --list
/usr/local/sbin/wazuh-restore.sh --from /var/backups/wazuh/wazuh-config-wazuh-mgr-01-20260809-013000.tar.gz

# 3. Проверка
/var/ossec/bin/cluster_control -l
/var/ossec/bin/agent_control -l | head -20
```

Скрипт восстановления перед изменениями:

* сверяет контрольную сумму архива;
* показывает, сколько агентов в копии и сколько сейчас, и предупреждает,
  если восстановление отключит часть уже работающих;
* сохраняет текущее состояние в отдельный архив `pre-restore-*`;
* проверяет конфигурацию через `wazuh-analysisd -t` и не запускает
  службу, если проверка не прошла.

Восстановление поверх работающего узла с живыми агентами может
оказаться хуже самой аварии — поэтому подтверждение спрашивается явно.

### Только ключи агентов

Частый случай: конфигурация в порядке, потерян `client.keys`.

```bash
/usr/local/sbin/wazuh-restore.sh --from <архив> --only-keys
```

## Выгрузка за пределы площадки

Используется rclone, уже настроенный в компании для выгрузки проектов
на Google Drive.

```bash
# проверка доступа
rclone lsd gdrive:

# что выгружается автоматически, ежедневно в 04:00
rclone copy /var/backups/wazuh gdrive:Backup/Wazuh/wazuh-mgr-01 --include 'wazuh-config-*'
```

Наружу уходят только конфигурации. Снапшоты индексов остаются на
площадке: выгружать сотни гигабайт ежедневно нереально, а выборочно —
означало бы решать за будущее расследование, какие данные ему
понадобятся.

Практическое следствие: после потери площадки система восстанавливается
за часы, но с пустой историей событий.

## Проверка восстановления

Резервная копия проверяется восстановлением, а не наличием файла.

**Раз в квартал** (30 минут):

```bash
# 1. Развернуть временную ВМ, поставить менеджер той же версии
# 2. Восстановить туда последнюю копию
/usr/local/sbin/wazuh-restore.sh --from <последний архив> --yes
# 3. Убедиться, что client.keys содержит ожидаемое число агентов
wc -l /var/ossec/etc/client.keys
# 4. Убедиться, что правила на месте
ls /var/ossec/etc/rules/ahp_*.xml
# 5. Погасить ВМ
```

**Раз в полгода**: восстановление индекса из снапшота в режиме
`--rename` и проверка, что данные читаются в интерфейсе.
