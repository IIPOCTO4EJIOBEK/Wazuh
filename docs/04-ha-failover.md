# 04. Отказоустойчивость

Резервирование, которое ни разу не проверяли, резервированием не
является. Этот документ описывает, что именно переживает отказ, что не
переживает, и как это проверить, не дожидаясь аварии.

---

## Уровни резервирования

### Индексер: кворум и реплики

Три узла, все могут быть выбраны мастером. Кворум — два из трёх.

* Отказ одного узла: кластер переходит в `yellow`, реплики становятся
  первичными шардами, поиск и запись продолжаются. Данные не теряются.
* Отказ двух узлов: кворум потерян, кластер останавливается. Это не
  дефект конструкции, а свойство кворума — защита от двух одновременных
  отказов потребовала бы пяти узлов.

Задержка перед перебалансировкой — 10 минут
(`index.unassigned.node_left.delayed_timeout`). Смысл: перезагрузка узла
на обновление занимает 3–5 минут, и копировать сотни гигабайт по сети
только для того, чтобы через минуту вернуть обратно, бессмысленно.

### Менеджеры: master и worker

Асимметрия здесь принципиальна, и её надо понимать явно.

| Функция | master | worker |
|---------|--------|--------|
| Приём событий от агентов | да | да |
| Анализ правилами | да | да |
| Active response | да | да |
| Wazuh API на чтение | да | да |
| **Регистрация новых агентов** | **да** | **нет** |
| **Изменение правил и групп** | **да** | **нет** |

Служба `wazuh-authd` работает только на master, ключи агентов создаются
там же. Поэтому при отказе master:

* уже зарегистрированные агенты продолжают слать события — их
  принимает worker;
* новые агенты зарегистрировать нельзя;
* переустановленная машина не сможет подключиться, пока master не
  вернётся.

Это приемлемо: регистрация — операция плановая, а приём событий —
непрерывная. Если master недоступен дольше суток, worker повышается до
master вручную (процедура ниже).

### Балансировщики: keepalived

Два узла, два независимых виртуальных адреса. Проверка живости —
`/etc/keepalived/check-haproxy.sh` — смотрит не только на процесс:

1. процесс haproxy существует;
2. служебный порт 8404 отвечает на `/healthz`;
3. хотя бы один менеджер доступен через балансировщик.

Третий пункт важнее первых двух: зависший haproxy с живым процессом —
типовая ситуация, при которой VIP остаётся на мёртвом узле.

Включён `nopreempt`: восстановившийся узел не забирает адрес обратно.
Лишнее переключение — это ещё один разрыв соединений четырёхсот агентов
ради ничего.

### Дашборды

Состояние хранится в индексе `.kibana`, сами узлы без состояния. Потеря
любого не требует восстановления — достаточно поднять новый и накатить
роль.

## Учения

Скрипт `scripts/failover-test.sh` проводит пять сценариев, после
каждого возвращая систему в исходное состояние.

```bash
cd wazuh-deploy/scripts

./failover-test.sh --scenario 1    # отказ узла индексера
./failover-test.sh --scenario 2    # отказ worker
./failover-test.sh --scenario 3    # отказ master
./failover-test.sh --scenario 4    # отказ балансировщика с VIP
./failover-test.sh --scenario 5    # отказ узла дашборда

./failover-test.sh --all --yes     # всё подряд, без вопросов
```

Когда проводить: раз в квартал и после каждого изменения топологии.
Время: вне рабочих часов, с предупреждением дежурного.

Главный показатель во всех сценариях один — не прервался ли приём
событий. Всё остальное вторично: пропущенное событие не восстановить,
а недоступный на минуту дашборд не стоит ничего.

## Повышение worker до master

Выполняется, когда master потерян надолго и нужна регистрация агентов.

```bash
# 1. Убедиться, что master действительно недоступен, а не разделён
#    сетью: два master в одном кластере разъедутся по конфигурации.
ping 10.5.2.85
ssh ansible@10.5.2.85 sudo /var/ossec/bin/wazuh-control status

# 2. На worker сменить тип узла
ssh ansible@10.5.2.86
sudo sed -i 's|<node_type>worker</node_type>|<node_type>master</node_type>|' \
    /var/ossec/etc/ossec.conf
sudo systemctl restart wazuh-manager

# 3. Перенаправить регистрацию на новый master
#    (на обоих балансировщиках)
sudo sed -i 's|10.5.2.85|10.5.2.86|' /etc/haproxy/haproxy.cfg
sudo systemctl reload haproxy
```

После возврата прежнего master **не запускать его как master** — сначала
переключить в worker, иначе в кластере окажется два мастера и
конфигурации разъедутся.

Постоянное закрепление изменений — правка `inventory/hosts.yml`
(группа `wazuh_manager_master`) и прогон:

```bash
ansible-playbook site.yml --tags manager,lb --ask-vault-pass
```

## Обновление без простоя

Порядок обратный установке: индексер, менеджеры, дашборды. Между
шагами — проверка.

```bash
# 1. Запретить перебалансировку на время работ
curl -k -u admin -X PUT 'https://10.5.2.81:9200/_cluster/settings' \
  -H 'Content-Type: application/json' \
  -d '{"persistent":{"cluster.routing.allocation.enable":"primaries"}}'

# 2. Узлы индексера по одному
ansible-playbook site.yml --tags indexer --limit wazuh-idx-01 --ask-vault-pass
# дождаться, пока узел вернётся, и только потом следующий

# 3. Вернуть перебалансировку, дождаться green
curl -k -u admin -X PUT 'https://10.5.2.81:9200/_cluster/settings' \
  -H 'Content-Type: application/json' \
  -d '{"persistent":{"cluster.routing.allocation.enable":null}}'

# 4. Менеджеры: сначала worker, потом master
ansible-playbook site.yml --tags manager --limit wazuh-mgr-02 --ask-vault-pass
ansible-playbook site.yml --tags manager --limit wazuh-mgr-01 --ask-vault-pass

# 5. Дашборды
ansible-playbook site.yml --tags dashboard --ask-vault-pass
```

Роль индексера делает шаги 1 и 3 автоматически при перезапуске службы —
руками они нужны только при работах вне Ansible.

Версии пакетов закреплены (`hold` / `versionlock`), поэтому `apt upgrade`
не утащит кластер на новую версию случайно. Обновление всегда
осознанное: меняется `wazuh_version` в `group_vars/all.yml`.

## Чего эта схема не переживёт

**Потерю площадки.** Все девять машин в одной сети. Смягчение — выгрузка
конфигураций через rclone за пределы площадки; восстановление на новом
месте занимает часы, исторические события теряются.

**Одновременный отказ двух узлов индексера.** Требует пяти узлов, для
сети такого размера неоправданно.

**Ошибку оператора.** Удалённый индекс восстанавливается из снапшота
(до суток данных теряется), удалённые правила — из этого репозитория,
удалённый `client.keys` — из ежедневной копии конфигурации.
