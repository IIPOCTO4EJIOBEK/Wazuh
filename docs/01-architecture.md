# 01. Архитектура

## Где размещается

Платформа ставится в сегмент мониторинга 10.5.2.0/24 — там же, где
Zabbix (10.5.2.74). Причина простая: у этого сегмента уже настроены
правила доступа ко всем остальным сетям компании, потому что система
мониторинга по определению должна дотягиваться везде. Заводить второй
такой сегмент означало бы дважды согласовывать одни и те же правила
межсетевого экрана.

## Потоки данных

```
  агент  ──1514/tcp──►  VIP 10.5.2.90  ──►  менеджер (любой)
                                              │
                                              ├─ анализ правилами
                                              ├─ active response ──► обратно на агент
                                              └─ alerts.json
                                                     │
                                                 filebeat
                                                     │ 9200/tcp, TLS
                                                     ▼
                                          индексер (все три узла)
                                                     │
                                             ┌───────┴────────┐
                                             ▼                ▼
                                        дашборд          снапшоты
                                       (443/tcp)         (NFS, ночью)
```

Регистрация агента идёт отдельным потоком на 1515/tcp и всегда
направляется на master: служба `wazuh-authd` работает только там,
и ключи агентов создаются только там.

## Почему такая топология

**Три узла индексера, а не два.** Кластеру нужен кворум, чтобы выбрать
мастера. Из двух узлов кворум — оба, то есть отказ любого останавливает
кластер целиком. Из трёх кворум — два: отказ любого одного узла ничего
не меняет. Три узла — минимальное количество, при котором резервирование
вообще работает.

**Один шард на узел плюс реплика.** Три первичных шарда распределяются
по трём узлам, реплики размещаются на соседях. Потеря узла означает
потерю одной копии каждого шарда, но не данных: реплика становится
первичным шардом автоматически.

**Два менеджера, а не три.** Менеджер не хранит данные и не выбирает
мастера голосованием — роли заданы в конфигурации. Второй узел нужен
для того, чтобы приём событий пережил перезагрузку первого, и этого
достаточно. Асимметрия здесь осознанная: приём событий переживает отказ
любого менеджера, регистрация новых агентов — только отказ worker.
Подробно об этом — в [04-ha-failover.md](04-ha-failover.md).

**Отдельные балансировщики, а не keepalived на менеджерах.** Так
проверка живости отделена от проверяемого: узел, который решает, куда
направлять поток, не совпадает с узлом, который этот поток
обрабатывает. Зависший менеджер продолжал бы считать себя живым.

**Два независимых VIP.** Авария в веб-интерфейсе не должна утаскивать
за собой приём событий. Сбор данных важнее их показа: пропущенное
событие не восстановить, а дашборд подождёт.

## Что происходит при отказах

| Отказ | Приём событий | Регистрация | Интерфейс | Поиск |
|-------|---------------|-------------|-----------|-------|
| один узел индексера | работает | работает | работает | работает |
| два узла индексера | останавливается | работает | не работает | не работает |
| worker-менеджер | работает | работает | работает | работает |
| master-менеджер | работает | **не работает** | работает (чтение) | работает |
| один балансировщик | работает | работает | работает | работает |
| один дашборд | работает | работает | работает | работает |
| хранилище снапшотов | работает | работает | работает | работает |

Строка про потерю двух узлов индексера — не оговорка, а свойство
кворума: три узла защищают от одного отказа, а не от двух. Защита от
двух одновременных отказов требует пяти узлов, и для сети такого
размера это неоправданно.

## Что не резервируется

**Площадка целиком.** Все девять машин стоят в одной сети и, скорее
всего, на одном гипервизоре или кластере гипервизоров. Отказ площадки
означает недоступность SIEM. Смягчение: копии конфигураций выгружаются
через rclone за пределы площадки, поэтому восстановление на новом месте
занимает часы, а не недели. Исторические события при этом теряются.

**Сеть площадки.** Отказ ядра сети делает недоступной и SIEM, и всё
остальное. Это осознанно принятый риск: отдельный канал для системы
мониторинга не строится.
