# 18. Проверка конфигурации по CIS: что делать с результатом

Выгрузка модуля SCA, политика `cis_win2022` — эталон CIS для Windows
Server 2022. В инвентаре проекта под эту политику подпадает pdc-hv0;
если выгрузка снята с другого узла, выводы по составу настроек
останутся теми же, а приоритеты стоит пересмотреть.

| | |
|---|---|
| Проверок | 359 |
| Пройдено | 93 |
| Не пройдено | 265 |
| Неприменимо | 1 |
| Оценка | 26% |

Для сравнения: pbx1 (Debian 11, эталон CIS) — 41%.

---

## Сначала о том, как это читать

**26% не означает «система защищена на четверть».** Эталон CIS —
максималистский документ: в нём есть и отключение SMBv1, и заголовок
предупреждения на экране входа, и запрет задачи «Заказ отпечатков». Оба
пункта весят в оценке одинаково, а стоят разного.

Гнаться за процентом бессмысленно и вредно: часть требований на
работающем сервере выполнять нельзя, а массовое применение эталона
одним заходом кладёт продуктивную систему. Работать нужно не с
процентом, а с тремя группами настроек, и первая из них к безопасности
как таковой отношения не имеет — она про то, работает ли наш SIEM.

---

## Группа 1. Настройки, без которых не работают наши же правила

Это самое ценное в выгрузке. Правила написаны, разложены и выглядят
рабочими — но на этом узле часть из них не сработает никогда, потому
что событий, на которых они построены, система не порождает.

### Командная строка в событии 4688

| Проверка | Результат |
|----------|-----------|
| 17.3.2 «Audit Process Creation» | **пройдена** |
| 18.9.3.1 «Include command line in process creation events» | **не пройдена** |

События запуска процессов пишутся, но **без командной строки**. Прямые
последствия:

* правило **100311** (удаление теневых копий: `vssadmin delete
  shadows`, `wbadmin delete catalog`) проверяет поле
  `win.eventdata.commandLine` — на этом узле оно пустое, правило не
  сработает никогда;
* правило **100313** (запуск PowerShell с `-enc`, `-w hidden`,
  `FromBase64String`) — то же самое;
* в разборе инцидента 01.07.2026
  ([16-incident-pdc-hv0.md](16-incident-pdc-hv0.md)) вопрос «с какими
  аргументами запускался `svhost.exe`» остался бы без ответа даже при
  установленном агенте.

Правила 100500 и 100502 из нового набора работают по полю
`newProcessName`, которое в событии есть всегда, — эти не пострадали.

### Запись блоков PowerShell

| Проверка | Результат |
|----------|-----------|
| 18.10.87.1 «Turn on PowerShell Script Block Logging» | **не пройдена** |
| 18.10.87.2 «Turn on PowerShell Transcription» | **не пройдена** |

Группа агентов `windows` читает канал
`Microsoft-Windows-PowerShell/Operational` с фильтром по событиям 4103
и 4104. Канал читается, событий в нём нет. Требование включить это
политикой записано в [06-agents.md](06-agents.md) — выгрузка
показывает, что на узле оно не выполнено.

### Правила сокращения направленных атак (ASR)

| Проверка | Результат |
|----------|-----------|
| 18.10.43.6.1.1 «Configure Attack Surface Reduction rules» | **не пройдена** |
| 18.10.43.6.1.2 «Set the state for each ASR rule» | **не пройдена** |

Правило **100532** ждёт событий 1121/1126 — блокировок по ASR. ASR не
настроен, событий не будет.

Отдельно стоит отметить, что среди правил ASR есть «Блокировать
создание процессов, порождённых командами PSExec и WMI». Это ровно тот
приём, которым на pdc-hv0 работал `winexe`. Настроенный ASR остановил
бы его без всякого SIEM.

### Устойчивость самой политики аудита

| Проверка | Результат |
|----------|-----------|
| 2.3.2.1 «Force audit policy subcategory settings to override category settings» | **не пройдена** |

Расширенные подкатегории аудита может перекрыть устаревшая политика
категорий, и тогда часть событий тихо перестанет писаться — без
ошибок и без следов. Это как раз тот случай, когда правило 100005
(«молчание агента на критичном узле») сработает, а причина будет не
там, где её станут искать.

**Исправлено в проекте:** `scripts/pilot/Enable-AdAuditPolicy.ps1`
теперь выставляет `SCENoApplyLegacyAuditPolicy`. Скрипт уже задавал
`ProcessCreationIncludeCmdLine_Enabled` и запись блоков PowerShell —
значит, на этом узле он просто не запускался.

Ещё 24 из 34 проверок раздела 17 не пройдены: изменение политики
аудита, использование привилегий, доступ к общим папкам, членство в
группах, состояние безопасности системы. Все эти подкатегории есть в
списке скрипта.

**Вывод по группе:** один запуск `Enable-AdAuditPolicy.ps1` на узле
закрывает бо́льшую часть, и это самая дешёвая работа из всех
перечисленных в документе. ASR настраивается отдельно.

| Проверка | Что не так | Как связано |
|----------|------------|-------------|
| 9.1.1, 9.2.1, 9.3.1 | **брандмауэр выключен во всех трёх профилях** | `winexe` пришёл по SMB. Ограничение доступа к 445 с рабочих подсетей закрыло бы путь |

и есть тот момент, который отсекается сетевым ограничением, а не
обнаружением.

## Группа 3. Остальное

Оставшиеся примерно 180 проверок — общее ужесточение: автозапуск со
съёмных носителей, печать по HTTP, настройки RPC, заголовок
предупреждения на экране входа, время простоя сеанса, установщик
приложений. Это правильные требования, но они не меняют картину
завтрашнего дня и применяются плановой работой через групповую
политику, а не срочно.

Одна проверка из списка невыполнима намеренно: **18.10.89.2.2
«Отключить удалённое управление через WinRM»**. WinRM нужен для
управления узлами, и отключать его мы не будем. Такие расхождения
правильнее фиксировать письменно — иначе при следующем разборе выгрузки
кто-нибудь честно попробует их «исправить».

---

## Порядок работ

**1. Запустить `Enable-AdAuditPolicy.ps1` на узле.** Ничего не ломает,
перезагрузки не требует, включает журналирование, на котором держится
половина набора правил.

```powershell
# Посмотреть, что скрипт сделает, ничего не меняя
.\Enable-AdAuditPolicy.ps1 -WhatIf
.\Enable-AdAuditPolicy.ps1
```

**2. Проверить результат событиями, а не повторной проверкой CIS.**
Проверка соответствия говорит, что параметр записан. Нужно другое:
что событие доехало до менеджера с нужными полями.

```powershell
# Запустить что-нибудь с приметной командной строкой
cmd /c "echo проверка-4688-командная-строка"
```

```bash
# На менеджере: событие пришло и командная строка в нём есть
grep -m1 'проверка-4688' /var/ossec/logs/archives/archives.json | \
  python3 -m json.tool | grep -i commandline
```

**3. Включить брандмауэр — с подготовкой, не сходу.** Включение на
удалённом узле без заранее разрешённых правил для RDP, WinRM и агента
Wazuh отрезает управление. Порядок: сначала правила, потом профиль
`Domain`, и только затем остальные.

**4. Отключить SMBv1 и «Диспетчер печати».** Перезагрузка, окно
обслуживания. На гипервизоре печать не используется, SMBv1 — тоже.

**5. Настроить ASR.** Начать с режима аудита: правила пишут события,
но не блокируют. Через пару недель посмотреть, что попало бы под
блокировку, и после этого включать.

**6. Всё остальное — групповой политикой, планово.** Отдельным
объектом политики для серверов, с обкаткой на одном узле.

---

## Что стоит завести отдельно

**Отслеживать оценку, а не разбирать выгрузку каждый раз.** Модуль SCA
считает оценку при каждом прогоне, и её падение — это либо откат
настроек, либо чужие руки. Правило на такое событие в наборе не
заведено: сначала нужно посмотреть на настоящее событие изменения
оценки на стенде, а без работающего менеджера имя поля можно только
угадать. Задача поставлена, но не сделана — и лучше это назвать, чем
записать в проект правило, про которое неизвестно, срабатывает ли оно.

**Снять выгрузку с остальных узлов.** По одному узлу видно
конфигурацию одного узла. Если те же 265 проверок не пройдены на
контроллере домена — приоритеты меняются полностью.
