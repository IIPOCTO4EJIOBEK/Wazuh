# 14. Пилот: виртуальные машины и запуск

## Что решено

Пилот разворачивается **в неотказоустойчивой конфигурации** — одна
машина вместо девяти. Источники на этапе пилота — Active Directory и
Bitrix, журналы направляются в приёмник в Москве.

| Задача | Ответственный |
|--------|---------------|
| Виртуальные машины для Wazuh | Валерий |
| Завернуть Active Directory | Дулепов |
| Завернуть Bitrix | Цеховской В. |

Решение про одну машину — правильное. Пилот отвечает на вопрос «доходят
ли события и дают ли правила осмысленную картину», а на этот вопрос
топология не влияет. Согласование девяти машин заняло бы больше времени,
чем сам пилот.

**Что при этом принимается сознательно:** отказ единственной машины
означает остановку сбора и потерю событий за время простоя.
На пилоте это допустимо, в постоянной эксплуатации — нет. Схема
отказоустойчивого варианта: [01-architecture.md](01-architecture.md).

### ВМ 1 — `wazuh-pilot`

Единственный узел платформы: хранение, анализ, интерфейс и приём syslog
на одной машине.

**Вычислительные ресурсы**

| Параметр | Значение | Почему столько |
|----------|----------|----------------|
| vCPU | 8 | разбор событий правилами — самая тяжёлая часть, она упирается в процессор |
| ОЗУ | 16 ГБ (24 ГБ комфортно) | 6 ГБ куче индексера, остальное файловому кэшу, менеджеру и интерфейсу |
| Тип | обычная ВМ, проброс устройств не нужен | |

**Диски — три отдельных тома, не один**

| Точка монтирования | Объём | Что там | Что будет, если объединить |
|--------------------|------:|---------|---------------------------|
| `/` | 60 ГБ | система, пакеты | — |
| `/var/lib/wazuh-indexer` | 250 ГБ | индексы событий | переполнение индексами останавливает **всю** систему, а не только поиск |
| `/var/ossec` | 100 ГБ | правила, ключи агентов, `alerts.json` | буфер при недоступности индексера окажется на системном томе |

Разделение — не формальность. Предполётная проверка отказывается
работать, если данные индексера лежат на корневом разделе, и делает это
намеренно.

Файловая система — `xfs` или `ext4`, безразлично. Тонкие диски
(thin provisioning) допустимы, но следите за пулом: индексы растут
предсказуемо и постоянно.

Расчёт объёма: два контроллера домена и три узла Bitrix дают около 125
событий в секунду, из них в индекс попадает примерно 15 процентов — это
около 1,9 ГБ в сутки. Реплик в одноузловой схеме нет. При хранении в 90
суток нужно порядка 170 ГБ; 250 ГБ дают запас на всплески и на
переиндексацию.

**Сеть**

| Параметр | Значение |
|----------|----------|
| Адрес | статический, сервер пилота `10.17.1.252` |
| Пилотный | `10.17.1.252` |
| Шлюз, DNS | как принято в сегменте; DNS обязателен — без него не разрешатся имена контроллеров домена |
| Интерфейс | один; резервирование делается на гипервизоре, см. [13-network-redundancy.md](13-network-redundancy.md) |
| Синхронизация времени | **обязательна**, тот же источник NTP, что у контроллеров домена |

Про время отдельно: расхождение часов между источником событий и
платформой ломает корреляцию. Подбор пароля и последующий успешный вход
окажутся в журнале в обратном порядке, и правило, которое их связывает,
не сработает. Предполётная проверка это контролирует.

**Что должно быть открыто на межсетевых экранах**

| Откуда | Куда | Порт | Зачем |
|--------|------|-----:|-------|
| `10.0.2.0/24` (контроллеры домена) | `wazuh-pilot` | 514/tcp | приём syslog |
| `10.0.1.0/24` (Bitrix) | `wazuh-pilot` | 514/tcp | приём syslog |
| узлы с агентами | `wazuh-pilot` | 1514/tcp, 1515/tcp | события и регистрация агентов |
| рабочие места ИТ | `wazuh-pilot` | 443/tcp | веб-интерфейс |
| рабочие места ИТ | `wazuh-pilot` | 22/tcp | администрирование |
| `wazuh-pilot` | `10.5.2.74` | 10051/tcp | метрики в Zabbix |
| `wazuh-pilot` | интернет | 443/tcp | репозиторий пакетов и базы уязвимостей |
| `wazuh-pilot` | `10.1.20.25` | 25/tcp | почтовые уведомления |

Доступ в интернет нужен на время установки и для обновления баз
уязвимостей. Если политика его запрещает, установка выполняется через
внутреннее зеркало репозитория — это отдельная договорённость, о которой
лучше знать заранее.

**Учётные записи и доступ**

* Учётная запись `ansible` с правом `sudo` без пароля, вход по ключу.
  Пароль для входа не нужен.
* Доступ по SSH с управляющей машины, откуда запускается развёртывание.
* Локальная учётная запись администратора на случай недоступности сети —
  консоль гипервизора.

**Состояние ОС при передаче**

- [ ] Ubuntu Server 24.04 LTS, установка минимальная, без графики
- [ ] Три тома размечены и смонтированы, записи в `/etc/fstab` есть
- [ ] Статический адрес, шлюз и DNS настроены, имя узла `wazuh-pilot`
- [ ] `chrony` синхронизирован (`timedatectl show -p NTPSynchronized`)
- [ ] `apt update && apt upgrade` выполнены
- [ ] Учётная запись `ansible` создана, ключ добавлен, `sudo` без пароля
- [ ] Снимок состояния (snapshot) сделан — откат перед повторной установкой

Ничего из состава Wazuh ставить руками не нужно: всё разворачивается
Ansible.

### ВМ 2 — `wef-collector`

Нужна, если Active Directory заворачивается штатным механизмом Windows
(рекомендуемый путь, разбор в следующем разделе). Собирает события с
контроллеров домена и отдаёт их в Wazuh с сохранением всех полей.

| Параметр | Значение |
|----------|----------|
| ОС | Windows Server 2019 или 2022, в домене |
| vCPU | 4 |
| ОЗУ | 8 ГБ |
| Диск система | 80 ГБ |
| Диск под журналы | 200 ГБ (`ForwardedEvents` растёт быстро) |
| Сеть | серверная Москвы, статический адрес |
| Роль | сборщик событий Windows + агент Wazuh |

Порты: контроллеры домена → сборщик 5985/tcp (WinRM), сборщик →
`wazuh-pilot` 1514/tcp и 1515/tcp.

**Отдельная машина под это не обязательна.** Сборщиком событий может
работать любой рядовой сервер домена — роль встроена в Windows и
включается командой `wecutil qc`. Если в московской серверной есть
сервер с запасом по диску, машину можно не заводить: экономится лицензия
Windows Server и один узел в обслуживании. Отдельная ВМ нужна, только
если подходящего сервера нет либо канал `ForwardedEvents` нежелательно
смешивать с рабочей нагрузкой.

## Создание ВМ на pdc-hv0

Гипервизор — Hyper-V на Windows Server 2022. Значения по умолчанию в нём
для наших задач не годятся: ниже команды с уже учтёнными поправками.

Всё то же самое собрано в готовые скрипты — их и стоит запускать, а
команды ниже оставлены для понимания, что именно происходит:

| Скрипт | Что делает | Где запускать |
|--------|-----------|---------------|
| [`scripts/pilot/New-WazuhPilotVM.ps1`](../scripts/pilot/New-WazuhPilotVM.ps1) | создаёт ВМ со всеми поправками к настройкам Hyper-V | на pdc-hv0 |
| [`scripts/pilot/prepare-ubuntu-node.sh`](../scripts/pilot/prepare-ubuntu-node.sh) | тома по UUID, имя, время, учётная запись, обновление | на самой ВМ, от root |
| [`scripts/pilot/Enable-AdAuditPolicy.ps1`](../scripts/pilot/Enable-AdAuditPolicy.ps1) | расширенный аудит, командная строка в 4688, журнал PowerShell | на контроллерах домена |

Все три идемпотентны и переносимы на отказоустойчивую схему —
отличаются только параметрами.

### wazuh-pilot

```powershell
$VM     = "wazuh-pilot"
$Path   = "D:\Hyper-V"                   # том, где лежат виртуальные машины
$ISO    = "D:\ISO\ubuntu-24.04-live-server-amd64.iso"
$Switch = "SET-Wazuh"                    # коммутатор серверной сети

New-VM -Name $VM -Generation 2 -MemoryStartupBytes 16GB `
       -NewVHDPath "$Path\$VM\$VM-os.vhdx" -NewVHDSizeBytes 60GB `
       -SwitchName $Switch -Path $Path

# Память фиксированная. Динамическая память и куча JVM несовместимы:
# гипервизор отбирает страницы, которые виртуальная машина считает
# своими, и сборка мусора начинает работать с диском.
Set-VMMemory $VM -DynamicMemoryEnabled $false -StartupBytes 16GB

Set-VMProcessor $VM -Count 8

# Отдельные диски под индексер и под рабочий каталог менеджера
New-VHD -Path "$Path\$VM\$VM-indexer.vhdx" -SizeBytes 250GB -Dynamic
New-VHD -Path "$Path\$VM\$VM-ossec.vhdx"   -SizeBytes 100GB -Dynamic
Add-VMHardDiskDrive $VM -Path "$Path\$VM\$VM-indexer.vhdx" -ControllerType SCSI
Add-VMHardDiskDrive $VM -Path "$Path\$VM\$VM-ossec.vhdx"   -ControllerType SCSI

# Ubuntu не загрузится с шаблоном Secure Boot по умолчанию
Set-VMFirmware $VM -SecureBootTemplate MicrosoftUEFICertificateAuthority

# Автоматические контрольные точки включены по умолчанию и заметно
# замедляют дисковые операции. Для узла с индексом это ощутимо.
Set-VM $VM -AutomaticCheckpointsEnabled $false

# Время берём с того же NTP, что и контроллеры домена. Два источника
# времени расходятся, а расхождение ломает корреляцию событий.
Disable-VMIntegrationService $VM -Name "Time Synchronization"

# Поведение при перезагрузке гипервизора
Set-VM $VM -AutomaticStartAction Start -AutomaticStartDelay 120 `
           -AutomaticStopAction ShutDown

Add-VMDvdDrive $VM -Path $ISO
Set-VMFirmware $VM -FirstBootDevice (Get-VMDvdDrive $VM)
Start-VM $VM
```

### wef-collector

Если решено заводить отдельной машиной.

```powershell
$VM = "wef-collector"
New-VM -Name $VM -Generation 2 -MemoryStartupBytes 8GB `

Set-VM $VM -AutomaticStartAction Start -AutomaticStartDelay 180
```

### Где размещать диски

Требования по производительности скромные: 125 событий в секунду дают
порядка сотни операций записи в секунду — это выдержит любой том
массива. Отдельный класс дисков под пилот заказывать незачем.

Важнее другое. **Не размещать на томе, где был сбой 09.06.2026.** Тогда
отказал массив FUJITSU ETERNUS_DXL, ошибка пришла на
`\Device\HarddiskVolume10`, и после восстановления том формально здоров.
Пока причина отказа не установлена окончательно, класть на него систему,
которая должна пережить следующий такой отказ, не стоит.

### Разметка дисков в Ubuntu

При установке размечается только системный диск. Остальные — после:

```bash
lsblk                                    # обычно sdb и sdc

mkfs.xfs /dev/sdb                        # 250 ГБ — индексер
mkfs.xfs /dev/sdc                        # 100 ГБ — менеджер
mkdir -p /var/lib/wazuh-indexer /var/ossec

# Монтирование по UUID, а не по имени: sdb и sdc могут поменяться
# местами после перезагрузки, и данные окажутся не на своём месте
blkid /dev/sdb /dev/sdc

cat >> /etc/fstab <<'EOF'
UUID=<uuid-sdb>  /var/lib/wazuh-indexer  xfs  defaults,noatime  0 2
UUID=<uuid-sdc>  /var/ossec              xfs  defaults,noatime  0 2
EOF

mount -a
df -h /var/lib/wazuh-indexer /var/ossec
```

`noatime` снижает лишнюю запись: индексер держит открытыми тысячи
файлов, и обновление времени доступа у каждого — чистые накладные
расходы.

## Три пути завернуть Active Directory

Это решение определяет, будут ли работать правила, уже написанные под
Active Directory. Разница существенная, поэтому разбор подробный.

> **Рекомендация: путь 2 — агент на двух контроллерах домена.**
> Меньше всего работы, ничего не теряется, открывается автоматическое
> реагирование в каталоге. Путь 1 — если политика запрещает ставить
> агент на контроллеры. Путь 3 — только если невозможны первые два.
>
> Обоснование выбора — в разделе «Чем именно платим за каждый путь»
> ниже.

### Путь 1 — сбор событий Windows и агент на сборщике

Контроллеры домена штатным механизмом Windows Event Forwarding
пересылают события на `wef-collector`. На сборщике стоит один агент
Wazuh, который читает канал `ForwardedEvents`.

| | |
|---|---|
| На контроллерах домена ставится | **ничего**, только групповая политика |
| Поля событий | сохраняются полностью |
| Правила 100300–100399 | **работают как написаны** |
| Машин под это | одна (`wef-collector`) |

Настройка в двух словах: на сборщике `wecutil qc`, на контроллерах —
политика «Configure target Subscription Manager», подписка на нужные
идентификаторы событий. Затем в конфигурации агента канал
`ForwardedEvents` вместо `Security`.

Это лучший вариант: контроллеры домена остаются нетронутыми, а платформа
получает события в том виде, на который рассчитаны правила.

### Путь 2 — агент Wazuh прямо на контроллерах домена (рекомендуется)

| | |
|---|---|
| На контроллерах ставится | агент Wazuh, две машины |
| Поля событий | сохраняются полностью |
| Правила | работают как написаны |
| Дополнительно | становится доступна блокировка учётной записи по инциденту |

Две машины — не четыреста. Если установка агента на контроллеры домена
согласуется, это самый короткий путь, и он же открывает автоматическое
реагирование в каталоге.

### Путь 3 — NXLog и syslog напрямую

Тот, который подразумевается формулировкой «перенаправить в сислог».
Работает, но с потерей.

| | |
|---|---|
| На контроллерах ставится | NXLog, две машины |
| Поля событий | **теряются**, если не настроить вывод в JSON |
| Правила 100300–100399 | **не сработают** — им нужны поля `win.system.*` |
| Что потребуется | отдельный набор декодеров и правил под формат NXLog |

Конфигурация NXLog с выводом в JSON и фильтром по идентификаторам
событий лежит в
[`integrations/syslog/nxlog-ad-to-syslog.conf`](../integrations/syslog/nxlog-ad-to-syslog.conf).
Она сохраняет имена полей, но структура отличается от той, что создаёт
агент: вместо `win.system.eventID` придёт `data.EventID`. Правила
придётся продублировать — это примерно день работы и вдвое больший объём
сопровождения.

**Рекомендация:** путь 2. Путь 1 — если политика запрещает ставить
агент на контроллеры домена. Путь 3 — только если невозможны первые два;
тогда в план пилота надо заложить день на второй набор правил и
удвоенное сопровождение дальше.

### Чем именно платим за каждый путь

Сравнение по объёму работы, а не по красоте схемы.

| | Путь 1 (WEF) | Путь 2 (агент на ДК) | Путь 3 (NXLog) |
|---|---|---|---|
| Машин завести | 1 (или занять сервер) | 0 | 0 |
| Поставить ПО на контроллеры | нет | агент, 2 шт. | NXLog, 2 шт. |
| Настроить | подписку WEF, WinRM, политику | ничего сверх установки | конфигурацию NXLog |
| Точек отказа добавляется | 1 (сборщик) | 0 | 0 |
| Правила AD | работают | работают | **переписать заново** |
| Блокировка учётной записи по инциденту | нет | **есть** | нет |
| Лицензия Windows Server | нужна, если новая ВМ | не нужна | не нужна |

Путь 1 выглядит аккуратнее, потому что на контроллеры ничего не
ставится. Но он добавляет машину, подписку, WinRM и единственную точку,
через которую идут все события каталога: остановился сборщик — пропал
весь Active Directory сразу.

Путь 2 — две установки агента и ноль новых сущностей. При этом только он
даёт возможность отключить скомпрометированную учётную запись
автоматически: действие выполняется на контроллере домена, а значит
агент там и нужен.

**Что требуется в любом случае.** Расширенный аудит Windows и запись
блоков PowerShell включаются групповой политикой независимо от способа
доставки. Без них события 4688, 4769 и 4104 просто не создаются, и
доставлять будет нечего. Состав политик — в
[06-agents.md](06-agents.md). Это первое, что стоит сделать: настройка
занимает полчаса и нужна при любом решении.

### Где место syslog

Отсюда следует более общий вывод, который стоит зафиксировать.

Syslog — не способ подключить Active Directory и Bitrix. Это способ
подключить то, **куда агент поставить нельзя**: маршрутизаторы MikroTik,
Nginx Proxy Manager, сетевое оборудование, гипервизоры сторонних
площадок, устройства печати. Такого в сети компании достаточно, и приём
syslog в пилоте остаётся включённым именно ради них.

Там, где агент поставить можно, он даёт заметно больше при меньших
усилиях. Пять машин — два контроллера домена и три узла Bitrix — это не
раскатка, это один рабочий день.

## Bitrix

Здесь ситуация проще, но с одной оговоркой.

Пересылка журналов настраивается конфигурацией
[`integrations/syslog/rsyslog-bitrix-forward.conf`](../integrations/syslog/rsyslog-bitrix-forward.conf):
журналы nginx, PHP и приложения заявок уходят по TCP с очередью на
диске — при обрыве канала события накапливаются и уходят после
восстановления связи.

Текстовые декодеры (`zayavka`, `sdp-sync`, `haproxy`) на пересланных
событиях работают: они разбирают строку, а не структуру Windows. Веб-атаки
и события приложения заявок обнаруживаются.

**Чего syslog не даёт: контроля целостности файлов.** Правила
100201–100205 следят за каталогом `/home/bitrix/www` — за появлением
новых PHP-файлов и подменой кода. Это самая ценная часть покрытия для
портала, и она требует агента: syslog не умеет наблюдать за файловой
системой.

Практический вывод: на узлах Bitrix ставить агент, а не настраивать
пересылку. Агент читает те же журналы nginx и приложения локально — и
дополнительно следит за каталогом портала. Настройка пересылки в этом
случае просто не нужна, и работы у Цеховского становится меньше, а не
больше.

Делается одной командой:

```bash
ansible-playbook -i inventory/pilot/hosts.yml playbooks/agents-linux.yml --ask-vault-pass
```

---

## Что теряется при передаче через syslog — общее правило

Стоит зафиксировать, потому что это касается любых источников.

| Возможность | Агент | Syslog |
|-------------|:-----:|:------:|
| Разбор текстовых журналов | да | да |
| Поля событий журнала Windows | да | нет (JSON — частично) |
| Контроль целостности файлов | да | нет |
| Инвентарь и поиск уязвимостей | да | нет |
| Проверка конфигурации по CIS | да | нет |
| Активное реагирование | да | нет |
| Буфер при обрыве канала | в памяти, минуты | на диске отправителя, сутки |

Syslog — способ получить события оттуда, куда агент поставить нельзя.
Там, где можно, агент даёт заметно больше.

## Развёртывание

Инвентарь пилота отделён от боевого: у него свои переменные, и
перепутать их нельзя.

```bash
cd wazuh-deploy/ansible

# 1. Секреты (одноразово)
cp group_vars/vault.yml.example group_vars/vault.yml
$EDITOR group_vars/vault.yml
ansible-vault encrypt group_vars/vault.yml

# 2. Проверить адрес пилота
grep -n "10.17.1.252" inventory/pilot/hosts.yml

# 3. Проверка машины до установки
ansible-playbook -i inventory/pilot/hosts.yml site.yml --tags preflight --ask-vault-pass

# 4. Установка целиком, около 40 минут
ansible-playbook -i inventory/pilot/hosts.yml site.yml --ask-vault-pass

# 5. Агенты на узлы Bitrix
ansible-playbook -i inventory/pilot/hosts.yml playbooks/agents-linux.yml --ask-vault-pass

# 6. Приёмка
../scripts/healthcheck.sh
```

Чем конфигурация пилота отличается от боевой (файл
`inventory/pilot/group_vars/all.yml`):

| Параметр | Боевая | Пилот | Почему |
|----------|--------|-------|--------|
| Шардов / реплик | 3 / 1 | 1 / 0 | на одном узле реплике негде разместиться, иначе состояние навсегда `yellow` |
| Куча индексера | 8 ГБ | 6 ГБ | память делят индексер, менеджер и интерфейс |
| Хранение | 400 суток | 90 суток | пилот короткий |
| Кластер менеджеров | включён | выключен | кластер из одного узла даёт только накладные расходы |
| Приём syslog | выключен | **включён** | так заходят AD и Bitrix |
| Заявки в ServiceDesk | с уровня 12 | выключены | правила ещё настраиваются, ложные срабатывания забьют очередь поддержки |
| Проверочный снапшот | делается | пропускается | общего хранилища под снапшоты ещё нет |

Почта и метрики в Zabbix включены с первого дня: пилот должен уметь
сообщить, что он сам перестал работать.

## Приёмка пилота

- [ ] Интерфейс открывается, вход выполняется
- [ ] События с контроллеров домена доходят и разбираются
- [ ] События Bitrix доходят и разбираются
- [ ] Тестовый вход с неверным паролем на контроллере домена поднял алерт
- [ ] Создание файла в `/home/bitrix/www` подняло правило 100202
- [ ] Правила прошли самопроверку при развёртывании
- [ ] Дашборды показывают данные, а не пустые панели
- [ ] Метрики платформы приходят в Zabbix
- [ ] Ежедневная копия конфигурации создаётся
- [ ] Замерен фактический поток событий в секунду и объём в сутки

Последний пункт — главный результат пилота помимо самой проверки правил.
Расчёт в [02-sizing.md](02-sizing.md) сделан по типовым значениям;
фактические числа позволят уточнить объёмы для отказоустойчивой схемы,
а не закладывать запас вслепую.

Разумный срок наблюдения — две недели. Первая неделя уйдёт на снятие
ложных срабатываний.

## Переход к отказоустойчивой схеме

Пилот не выбрасывается.

| Что переиспользуется | Как |
|----------------------|-----|
| Правила, декодеры, списки | без изменений, лежат в репозитории |
| Настроенные исключения ложных срабатываний | без изменений |
| Дашборды | без изменений |
| Пересылка syslog от AD и Bitrix | адрес приёмника меняется на виртуальный |
| Сама машина пилота | становится одним из узлов либо остаётся стендом |
| Исторические события пилота | переносятся снапшотом, если нужны |

Порядок перехода: развернуть отказоустойчивый комплект по
[03-installation.md](03-installation.md), перевести отправителей syslog
на новый адрес, перерегистрировать агенты. Пилот при этом продолжает
работать до момента переключения.

Один параметр придётся поменять осознанно: в пилоте политика хранения
удаляет данные через 90 суток. В боевой схеме — 400.

## Риски, принятые сознательно

| Риск | Следствие | Чем закрывается на этапе пилота |
|------|-----------|--------------------------------|
| Отказ единственной машины | сбор останавливается, события за простой теряются | снимок ВМ, ежедневная копия конфигурации, срок пилота ограничен |
| Нет резервного хранилища снапшотов | потеря машины уносит исторические события | на пилоте они не ценны |
| Диск переполнился | запись останавливается | отдельные тома, порог тревоги в Zabbix, срок хранения 90 суток |
| Syslog по TCP без шифрования | события идут по сети открытым текстом | внутренняя сеть; для боевой схемы предусмотреть TLS или туннель |
| Правила AD не сработают при пути 3 | пропуск событий каталога | выбрать путь 1 или 2, либо заложить время на второй набор правил |

Последняя строка — единственный риск, который может обесценить пилот.
Решение по способу подключения Active Directory стоит принять до выдачи
виртуальных машин, потому что от него зависит, нужна ли вторая машина.
