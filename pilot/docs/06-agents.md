# 06. Агенты

## Группы и от чего они зависят

Агент состоит в нескольких группах одновременно, настройки складываются.
Файл группы лежит в `rules/agent-groups/<имя>.conf` и раскладывается на
master; оттуда он расходится по агентам сам.

| Группа | Кому | Что добавляет |
|--------|------|---------------|
| `default` | всем | инвентарь, проверка конфигурации по CIS, ограничение потока |
| `linux` | серверам Linux | системные журналы, journald, аудит ядра, целостность `/etc` |
| `windows` | всем Windows | журналы Security/System/Application с фильтром, PowerShell, Defender, автозапуск |
| `bitrix-web` | web01, web02, b24-web-01 | реальное время на `/home/bitrix/www`, журналы nginx и PHP |
| `database` | СУБД портала | журналы MySQL, состояние репликации |
| `dmz` | HAProxy, NPM | журналы балансировщика и прокси, срок действия сертификатов |
| `dc` | контроллерам домена | журнал каталога, репликация, DNS, события 4662 и 5136–5141 |
| `hyperv` | pdc-hv0 | каналы Hyper-V, MPIO, NTFS, состояние дисков и ВМ |
| `mssql` | PDC-DB1 | журналы MSSQL, ERRORLOG |
| `workstation` | рабочим станциям | облегчённый профиль, съёмные носители |

Почему это важно: рабочей станции не нужен разбор журналов MSSQL, а
контроллеру домена — мониторинг каталога Bitrix. Один общий профиль на
400 машин означал бы либо дыры в покрытии, либо поток событий, который
никто не читает.

Изменение конфигурации группы:

```bash
$EDITOR rules/agent-groups/windows.conf
cd ansible
ansible-playbook site.yml --tags content --ask-vault-pass
```

Проверить, что менеджер принял файл:

```bash
ssh ansible@10.5.2.85 sudo /var/ossec/bin/verify-agent-conf
```

## Раскатка на Windows через групповую политику

### Подготовка сетевого ресурса

На pdc-hv0 (10.2.27.118):

```
\\10.2.27.118\wazuh$\
    wazuh-agent-4.14.7-1.msi
    Install-WazuhAgent.ps1
    authd.pass
```

Права: чтение для группы `Domain Computers`, полный доступ для
администраторов домена. Пароль регистрации читают компьютеры, а не
пользователи — поэтому именно `Domain Computers`.

```powershell
New-SmbShare -Name 'wazuh$' -Path 'V:\wazuh' -ReadAccess 'AHPROSTORY\Domain Computers'
icacls V:\wazuh /grant 'AHPROSTORY\Domain Computers:(OI)(CI)R'
```

### Политика

1. Создать GPO «Установка агента Wazuh», привязать к OU с компьютерами.
2. Конфигурация компьютера → Настройки → Панель управления →
   Запланированные задания → Немедленная задача (Windows 7 и выше).
3. Параметры задания:

```
Учётная запись:  NT AUTHORITY\SYSTEM
Наивысшие права: да
Действие:        powershell.exe
Аргументы:       -NoProfile -ExecutionPolicy Bypass -File
                 \\10.2.27.118\wazuh$\Install-WazuhAgent.ps1
```

Скрипт идемпотентен: на машине с уже установленным агентом нужной
версии он завершается сразу. Поэтому задание может быть постоянным —
новые машины получат агент при первом применении политики.

Группа агента определяется автоматически по роли машины: рабочая
станция, контроллер домена, сервер с Hyper-V или MSSQL.

### Контроль раскатки

Скрипт пишет результат в журнал приложений Windows с источником
`WazuhAgentDeploy`. Отчёт по домену:

```powershell
$computers = Get-ADComputer -Filter * | Select-Object -ExpandProperty Name

$computers | ForEach-Object {
    $r = Get-WinEvent -ComputerName $_ -FilterHashtable @{
        LogName='Application'; ProviderName='WazuhAgentDeploy'
    } -MaxEvents 1 -ErrorAction SilentlyContinue
    [pscustomobject]@{
        Компьютер = $_
        Результат = if ($r) { $r.LevelDisplayName } else { 'нет данных' }
        Время     = $r.TimeCreated
    }
} | Export-Csv -Path wazuh-rollout.csv -Encoding UTF8 -NoTypeInformation
```

Со стороны Wazuh:

```bash
curl -sk -H "Authorization: Bearer $TOKEN" \
  'https://10.5.2.90:55000/agents?status=never_connected&pretty'
```

## Политики аудита Windows

Без включённого расширенного аудита правила 100300–100399 работать не
будут: события просто не создаются. Это делается отдельной групповой
политикой, один раз.

### Обязательный минимум

Конфигурация компьютера → Политики → Конфигурация Windows → Параметры
безопасности → Расширенная настройка политики аудита:

| Категория | Подкатегория | Режим |
|-----------|--------------|-------|
| Вход в систему | Вход в систему | Успех и отказ |
| Вход в систему | Выход из системы | Успех |
| Вход в систему | Блокировка учётной записи | Успех |
| Вход в систему | Специальный вход | Успех |
| Управление учётными записями | Управление учётными записями пользователей | Успех и отказ |
| Управление учётными записями | Управление группами безопасности | Успех и отказ |
| Подробное отслеживание | Создание процесса | Успех |
| Доступ к службе каталогов | Доступ к службе каталогов | Успех и отказ |
| Доступ к службе каталогов | Изменения службы каталогов | Успех |
| Отслеживание политик | Изменение политики аудита | Успех и отказ |
| Доступ к объектам | Доступ к объектам ядра | Успех и отказ |

Отдельно включить командную строку в событии 4688 — без неё правила на
запуск PowerShell и `vssadmin` бесполезны, потому что видно имя
процесса, но не аргументы:

```
Конфигурация компьютера → Административные шаблоны → Система →
  Аудит создания процессов →
  «Включать командную строку в события создания процессов» = Включено
```

### Запись блоков PowerShell

```
Конфигурация компьютера → Административные шаблоны → Компоненты Windows →
  Windows PowerShell →
    Включить регистрацию блоков сценариев = Включено
    Включить регистрацию модулей = Включено
```

Это источник событий 4103 и 4104, на которых построено правило 100313
(обфусцированный запуск PowerShell).

### Проверка

```powershell
auditpol /get /category:*
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Audit' -Name ProcessCreationIncludeCmdLine_Enabled
```

### Sysmon — по желанию

Конфигурация группы `windows` читает канал Sysmon, если он есть. Если
Sysmon не установлен, агент не найдёт канал и продолжит работу без него.

Sysmon даёт заметно более полную картину (сетевые соединения процессов,
создание потоков, доступ к процессам), но увеличивает поток примерно в
2,5 раза. Решение о его установке принимается после того, как система
проработает месяц без него и станет понятен базовый объём.

## Раскатка на Linux

```bash
cd wazuh-deploy/ansible

# все серверы из инвентаря
ansible-playbook playbooks/agents-linux.yml --ask-vault-pass

# отдельная группа
ansible-playbook playbooks/agents-linux.yml --limit agents_bitrix --ask-vault-pass
```

Плейбук идёт партиями по 25 процентов узлов: одновременная регистрация
всех агентов создаёт очередь в `wazuh-authd`, и часть попыток
завершается неудачей.

Для узлов вне инвентаря (машины подрядчиков, разовые установки):

```bash
scp agents/linux/install-wazuh-agent.sh root@узел:/tmp/
ssh root@узел '/tmp/install-wazuh-agent.sh --password "пароль"'
```

Скрипт сам определяет группы по установленным службам: наличие
`/home/bitrix/www` даёт `bitrix-web`, работающий haproxy — `dmz`, и так
далее.

## Приём агента: что должно произойти

1. Агент обращается на 10.5.2.90:1515, передаёт пароль и имя.
2. Балансировщик направляет запрос на master (worker регистрацию не
   принимает).
3. `wazuh-authd` создаёт ключ и записывает его в `client.keys`.
4. Ключ расходится по кластеру (обычно за минуту).
5. Агент подключается на 1514 к любому менеджеру.
6. Менеджер отдаёт конфигурацию групп; агент применяет её и
   перезапускает модули.

Проверка на агенте:

```bash
grep -E "Connected to the server|Valid key" /var/ossec/logs/ossec.log | tail -5
```

```powershell
Select-String -Path 'C:\Program Files (x86)\ossec-agent\ossec.log' -Pattern 'Connected to the server' | Select-Object -Last 3
```

Проверка на менеджере:

```bash
/var/ossec/bin/agent_control -l | grep <имя>
```

## Перерегистрация после переустановки машины

Включён режим `force`: имя агента можно переиспользовать, если прежний
агент с этим именем отключён более часа. Без этого переустановленная
машина не смогла бы подключиться, а удалять её вручную пришлось бы
каждый раз.

Если машина переустановлена только что и час ещё не прошёл — удалить
прежнюю запись:

```bash
/var/ossec/bin/manage_agents -r <id>
```

## Удаление агента

```bash
# на менеджере
/var/ossec/bin/manage_agents -r <id>

# на узле Linux
apt purge wazuh-agent   # или dnf remove
rm -rf /var/ossec

# на узле Windows
msiexec /x {идентификатор} /q
```

Уволенные и списанные машины надо снимать с учёта: агенты в состоянии
`never_connected` и `disconnected` накапливаются и портят отчётность о
покрытии сети. Правило 100005 при этом продолжает считать их
отсутствующими критичными узлами.
