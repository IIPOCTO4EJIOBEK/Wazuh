# 03. Установка

Порядок шагов обязателен. Индексер должен быть готов до менеджера
(filebeat при старте создаёт шаблон индексов), менеджер — до дашборда
(дашборду нужен работающий API), балансировщик — после всех, потому что
его проверки живости обращаются к реальным службам.

Полное развёртывание с нуля занимает около полутора часов, из них
примерно час — ожидание запуска служб.

---

## 0. Подготовка

### Виртуальные машины

Девять ВМ по [01-architecture.md](01-architecture.md), Ubuntu 24.04 LTS
(поддерживается и 22.04, и RHEL-совместимые 8/9).

На узлах индексера данные должны лежать на **отдельном томе**,
смонтированном в `/var/lib/wazuh-indexer`. Проверка `preflight`
откажется работать, если это не так, и правильно сделает: переполнение
данных на корневом разделе останавливает операционную систему целиком.

```bash
# на каждом узле индексера
lsblk                                  # найти второй диск, например /dev/sdb
mkfs.xfs /dev/sdb
mkdir -p /var/lib/wazuh-indexer
echo '/dev/sdb /var/lib/wazuh-indexer xfs defaults,noatime 0 2' >> /etc/fstab
mount -a
```

### Доступ Ansible

На всех девяти узлах: учётная запись `ansible`, ключ, sudo без пароля.

```bash
# с управляющей машины
ssh-copy-id ansible@10.5.2.81   # и так далее по списку
ansible -i inventory/hosts.yml all -m ping
```

### Управляющая машина

```bash
sudo apt install ansible python3-pip
pip3 install passlib bcrypt        # для хеширования паролей индексера
ansible-galaxy collection install community.general community.crypto ansible.posix
```

`passlib` и `bcrypt` обязательны: без них шаблон `internal_users.yml`
не соберётся, и плагин безопасности индексера не примет учётные записи.

### Хранилище снапшотов

На 10.1.222.81 (сервер резервных копий):

```bash
mkdir -p /srv/wazuh-snapshots
chown 1000:1000 /srv/wazuh-snapshots    # UID службы wazuh-indexer

cat >> /etc/exports <<'EOF'
/srv/wazuh-snapshots 10.5.2.81(rw,sync,no_subtree_check,no_root_squash) \
                     10.5.2.82(rw,sync,no_subtree_check,no_root_squash) \
                     10.5.2.83(rw,sync,no_subtree_check,no_root_squash)
EOF

exportfs -ra
```

Ресурс должен быть не меньше 1 ТБ: тридцать инкрементальных снапшотов
при суточном приросте около 6 ГБ занимают порядка 400–600 ГБ, остальное
— запас на пики и на восстановление.

### Записи DNS

```
wazuh.ahprostory.ru          A   10.5.2.91
wazuh-agents.ahprostory.ru   A   10.5.2.90
```

## 1. Секреты

```bash
cd wazuh-deploy/ansible
cp group_vars/vault.yml.example group_vars/vault.yml
```

Сгенерировать значения:

```bash
# ключ кластера менеджеров — ровно 32 символа
openssl rand -hex 16

# пароли (по одному на каждую учётную запись из файла)
openssl rand -base64 18 | tr -d '/+=' | head -c 16; echo
```

Требования к паролям индексера: не короче 12 символов, обязательно
строчные, заглавные, цифра и спецсимвол. Символы `" ' \ $ `` в паролях
не использовать — они ломают Java-конфигурации и хранилище filebeat.

```bash
ansible-vault encrypt group_vars/vault.yml
```

Файл `group_vars/vault.yml` внесён в `.gitignore` и в репозиторий не
попадает ни в открытом, ни в зашифрованном виде.

## 2. Предполётная проверка

```bash
ansible-playbook site.yml --tags preflight --ask-vault-pass
```

Проверяются версия ОС, память, место, отдельный том под данные
индексера, синхронизация времени и доступность репозитория Wazuh.

Расхождение часов — самая недооценённая проблема. События с разных
узлов лягут в индекс с неверными метками, и корреляция по времени
перестанет работать: подбор пароля и последующий успешный вход окажутся
в обратном порядке.

---

## 3. Сертификаты

```bash
ansible-playbook site.yml --tags certs --ask-vault-pass
```

Выпускается собственный УЦ и сертификаты для всех узлов. Файлы остаются
на управляющей машине в `ansible/files/wazuh-certificates` (каталог в
`.gitignore`).

**Эти файлы нужно сохранить.** Без корневого ключа перевыпуск
сертификата для нового узла невозможен — придётся перевыпускать все и
перезапускать весь кластер. Место хранения: то же, где хранятся другие
ключи компании, не в этом репозитории.

Проверка:

```bash
openssl x509 -in files/wazuh-certificates/wazuh-idx-01.pem -noout -subject -dates -ext subjectAltName
```

В subject должно быть `CN=wazuh-idx-01,OU=IT Security,O=AH Prostory,C=RU`
— эта строка посимвольно совпадает с `plugins.security.nodes_dn` в
конфигурации индексера. Расхождение хотя бы в пробеле означает, что
узлы не соберутся в кластер.

---

## 4. Индексер

```bash
ansible-playbook site.yml --tags indexer --ask-vault-pass
```

Узлы поднимаются по одному (`serial: 1`). После установки выполняется
`securityadmin.sh`, который загружает учётные записи и роли, затем
создаётся шаблон индексов и политика хранения.

Проверка:

```bash
curl -k -u admin:ПАРОЛЬ https://10.5.2.81:9200/_cluster/health?pretty
```

Ожидается `"status": "green"` и `"number_of_nodes": 3`. Состояние
`yellow` сразу после установки — норма (индексов ещё нет, реплики
размещать не на чем), но после появления данных должно стать `green`.

Если узлы не видят друг друга — почти всегда это несовпадение DN в
сертификатах или закрытый порт 9300. Разбор — в
[11-troubleshooting.md](11-troubleshooting.md).

## 5. Менеджеры

```bash
ansible-playbook site.yml --tags manager --ask-vault-pass
```

Сначала master, затем worker. После установки раскладываются правила,
декодеры, списки, конфигурации групп агентов и скрипты активного
реагирования, а затем прогоняются самопроверки: образцы событий
пропускаются через `wazuh-logtest`, и play падает, если хоть одно
собственное правило не сработало.

Эта проверка стоит нескольких секунд и закрывает самую неприятную
ошибку: правило с опечаткой в регулярном выражении молчит и выглядит
точно так же, как правило, для которого просто не было событий.

Проверка:

```bash
ssh ansible@10.5.2.85 sudo /var/ossec/bin/cluster_control -l
```

Ожидаются оба узла: master и worker.

## 8. Резервирование и интеграции

```bash
ansible-playbook site.yml --tags backup --ask-vault-pass
ansible-playbook site.yml --tags integrations --ask-vault-pass
```

Плейбук резервирования не просто настраивает расписание — он делает
проверочный снапшот и падает, если тот не собрался. Резервное
копирование, которое настроили и не проверили, резервным копированием
не является.

## 9. Агенты

Linux — через Ansible:

```bash
ansible-playbook playbooks/agents-linux.yml --ask-vault-pass
```

Windows — через групповую политику, см. [06-agents.md](06-agents.md).

Раскатывать сразу на все 400 машин не нужно. Разумный порядок:

1. 5–10 рабочих станций ИТ-отдела — сутки наблюдения за потоком;
2. серверы Linux и Windows — ещё сутки;
3. контроллеры домена — отдельно, с проверкой нагрузки;
4. остальные рабочие станции волнами по 50–80 машин.

Причина не в нагрузке на агенты, а в шуме: первая партия покажет, какие
правила придётся настраивать под конкретную инфраструктуру, и лучше
понять это на десяти машинах, чем на четырёхстах.

## 10. Приёмка

```bash
../scripts/healthcheck.sh
ansible-playbook playbooks/healthcheck.yml --ask-vault-pass
```

Приёмочный список:

- [ ] Кластер индексера green, три узла
- [ ] Кластер менеджеров: master и worker на связи
- [ ] Алерты появляются в `wazuh-alerts-*` (проверить за последний час)
- [ ] Дашборды открываются по `https://wazuh.ahprostory.ru`
- [ ] Оба VIP отвечают, переключение проверено (`failover-test.sh --scenario 4`)
- [ ] Проверочный снапшот собран
- [ ] Тестовый алерт создал заявку в ServiceDesk Plus
- [ ] Метрики Wazuh приходят в Zabbix
- [ ] Пароли по умолчанию изменены (`wazuh`, `wazuh-wui`, `admin`, `kibanaserver`)
- [ ] Сертификаты сохранены за пределами репозитория
- [ ] Проведены учения по отказоустойчивости, результат внесён в журнал

Проверка активного реагирования на тестовой машине:

```bash
# с любого узла: пять неудачных входов подряд
for i in $(seq 1 8); do ssh неверный@10.0.1.220; done

# на web01 должно появиться правило блокировки
ssh ansible@10.0.1.220 sudo nft list chain inet wazuh input
# и запись в журнале реагирования
ssh ansible@10.0.1.220 sudo grep ahp-ar /var/ossec/logs/active-responses.log
```

## Повторный запуск

Все плейбуки идемпотентны: повторный прогон `site.yml` на работающей
системе ничего не ломает и показывает расхождения конфигурации.

Регулярная проверка дрейфа (кто-то поправил файл на узле руками):

```bash
ansible-playbook site.yml --check --diff --ask-vault-pass
```

Вывод покажет, чем состояние узлов отличается от репозитория.
