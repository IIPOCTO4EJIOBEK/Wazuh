## 1. AD-авторизация для входа в дашборд (сделано)

Вход в Wazuh Dashboard теперь работает по доменным учётным данным (Active Directory `rusagroeco.ru`), по образцу Zabbix.

### Настройки (файл `/etc/wazuh-indexer/opensearch-security/config.yml`)

Домен `ldap_auth_domain` (order 2, basic challenge):

```yaml
authc:
  ldap_auth_domain:
    description: "LDAP / Active Directory authentication (AD rusagroeco.ru)"
    http_enabled: true
    transport_enabled: true
    order: 2
    http_authenticator:
      type: basic
      challenge: true
    authentication_backend:
      type: ldap
      config:
        enable_ssl: false
        enable_start_tls: false
        enable_ssl_client_auth: false
        verify_hostnames: false
        hosts:
          - 10.1.20.21:389            # AD-контроллер (как в Zabbix)
        connect_timeout: 5000
        response_timeout: 5000
        bind_dn: "CN=zabbix_tech,OU=Tech Users,OU=Special,DC=rusagroeco,DC=ru"
        password: "<пароль техаккаунта хранится в защищённом хранилище>"
        userbase: "DC=rusagroeco,DC=ru"
        usersearch: "(sAMAccountName={0})"
        username_attribute: "sAMAccountName"   # ВАЖНО: иначе username = полный DN
```

### Ключевые подводные камни (важно для будущих работ!)

1. **Wazuh Indexer = форк OpenSearch Security 1.x** — LDAP-сервер задаётся ключом **`hosts:`** (без схемы: `10.1.20.21:389`), а НЕ `servers: ldap://...` (это формат OpenSearch 2.x).
   - Симптом при неверном ключе: в `/var/log/wazuh-indexer/wazuh-ahp.log` ldaptive ходит на **`localhost:389`** → `Unable to connect to any of those ldap servers [localhost]`, все входы 401.
2. **Обязателен `username_attribute: sAMAccountName`** — без него пользователь представляется полным DN (`CN=...`), и маппинги ролей по имени (`tsekhovskoy.va`) не работают.
3. Применение конфига — только через securityadmin (файл на диске сам по себе не подхватывается):

```bash
cd /usr/share/wazuh-indexer/plugins/opensearch-security/tools
OPENSEARCH_JAVA_HOME=/usr/share/wazuh-indexer/jdk ./securityadmin.sh \
  -h 10.17.1.252 -p 9200 \
  -cacert /etc/wazuh-indexer/certs/root-ca.pem \
  -cert /etc/wazuh-indexer/certs/admin.pem \
  -key /etc/wazuh-indexer/certs/admin-key.pem \
  -cd /etc/wazuh-indexer/opensearch-security -nhnv
# Успех: "SUCC: Expected 10 config types ... Done with success"
```

### Проверка

```bash
# LDAP-пользователь аутентифицируется, роли read-only:
curl -sk -u "zabbix_tech:<пароль>" \
  https://10.17.1.252:9200/_plugins/_security/authinfo
# → user_name: zabbix_tech, roles: [own_index, kibana_read_only, wazuh_reader]

# Дашборд принимает AD-пользователя:
curl -sk -u "zabbix_tech:<пароль>" https://10.17.1.252:443/api/status   # HTTP 200
curl -sk -u "zabbix_tech:WRONG"           https://10.17.1.252:443/api/status   # HTTP 401
```

## 2. Права пользователей (по образцу Zabbix)

В Zabbix: `tsekhovskoy.va` = **Super admin**, обычные пользователи = **User** (только просмотр).
В Wazuh сделано то же самое через `/etc/wazuh-indexer/opensearch-security/roles_mapping.yml`:

| Пользователь | Роль | Права |
|---|---|---|
| `tsekhovskoy.va` | `all_access` | **Администратор** (полный доступ), как Super admin в Zabbix |
| `*` (все AD-пользователи) | `wazuh_reader` + `kibana_read_only` | **Только просмотр**: чтение `wazuh-alerts-*`, `wazuh-states-vulnerabilities-*`, без изменений |

Фактические маппинги:

```yaml
all_access:
  backend_roles: [admin]
  users: [tsekhovskoy.va]
wazuh_reader:
  users: [auditor, "*"]
kibana_read_only:
  users: ["*"]
```

Проверено на дашборде: вход `tsekhovskoy.va` (доменный пароль) → Roles: `own_index`, `kibana_read_only`, `all_access`, `wazuh_reader`. Backend roles — 0 (роли по имени пользователя, не по группам AD).

> Примечание: пароль `tsekhovskoy.va` из старых заметок AD **отвергает** (устарел, ошибка 52e) — пользователь входит своим актуальным доменным паролем.

## 3. Починка «No matching indices found: wazuh-states-vulnerabilities-*»

### Симптом
Дашборд (виджеты уязвимостей/инвентаря) выдавал: `No indices match pattern "wazuh-states-vulnerabilities-*"`.

### Причина
- Индексы `wazuh-states-vulnerabilities-wazush` и `wazuh-states-inventory-*-wazush` существовали, но были **пустые (0 документов)**;
- в их маппинге и в composable-шаблонах **не было поля `@timestamp`**, а data view `wazuh-states-vulnerabilities-*` объявлен с timefield `@timestamp` → кибана считала паттерн невалидным.

### Исправление (20.08.2026)
1. Добавлен `@timestamp: {type: date}` в маппинг **всех существующих states-индексов**:
   ```bash
   curl -sk --cert admin.pem --key admin-key.pem -X PUT \
     https://10.17.1.252:9200/wazuh-states-vulnerabilities-wazush/_mapping \
     -H 'Content-Type: application/json' \
     -d '{"properties":{"@timestamp":{"type":"date"}}}'
   ```
   (то же для 13 индексов `wazuh-states-inventory-*-wazush`).
2. Обновлены **все 14 composable-шаблонов** `wazuh-states-*-wazush_template` (PUT `/_index_template/<name>` с добавленным `@timestamp`) — новые индексы будут создаваться корректно.
3. Проверка: `GET /api/index_patterns/_fields_for_wildcard?pattern=wazuh-states-vulnerabilities-*` → 48 полей, включая `@timestamp`.

### Ограничение
Данных по-прежнему **нет**: на менеджере **0 агентов** (`agent_control -l` — только ID 000 `wazush (server)`). Дашборды «Уязвимости» и «Инфраструктура» пустые, пока не подключены wazuh-агенты.
